### [2026-08-07] Target: [mafgenComparison.md]
- THE .000001 LITERAL: ROOT CAUSE FOUND, and it is a general defect in XCOM-I, not anything specific to this literal or to HAL/S. XCOM-I/ibmFloat.c, ibm_dp_from_double() ends with
      //f = llround(d);
      f = (long long)(d + 0.5);
  The IBM mantissa lands in [2^52, 2^53), where the spacing between doubles is exactly 1.0, so d + 0.5 is not representable and rounds to even. An odd mantissa is therefore pushed UP one ULP; an even one is left alone. Measured on the real C function: 100% of odd mantissas corrupted, 0% with llround, which is the line already commented out directly above.
- That is exactly our case. ...ED8D has an odd mantissa (4722366482869645) and becomes ...ED8E; the dump's ...ED8C is even and survives untouched. Confirmed against the built function: ibm_dp_to_double(ED8D) then re-encoding gives ED8E, while ED8C round-trips to itself, and 1800.0 is unaffected because it is exactly representable either way.
- Chain, end to end: GEIORB compiles `1.0E-6` from its own source correctly to ED8D; PASS3 writes GEIORB's literal pool into ##GEIORB.sdf, where the doubleword sits at 0x76A8 immediately followed by 1800.0, the other literal from the same two source lines. GO8ORB, GO2ORB, GO1ASC and GO3ENT include an *_HFE template and inherit those literals; somewhere on that path the value passes through a C double and ibm_dp_from_double turns ED8D into ED8E. Eighteen units that compile the literal from their own source never take that path and are correct.
- IMPORTANT: fixing this does NOT make the comparison match. Our value becomes ED8D and the dump holds ED8C, so a one-ULP difference remains — but it becomes a difference where OUR value is defensibly right, which is precisely the -2 "suspected original-compiler defect" case PR #33 was written for. Before the fix we could not claim that, because our own value was wrong too.
- The fix is one line and is NOT applied: ibm_dp_from_double is used by everything XCOM-I builds, and rebuilding HALSFC would invalidate the sweep in progress. Verified in a copy: scratchpad/ibmFloat-fixed.c.
- Also corrected: modules/sdf's parseConstantValueCell was NOT wrong. Its `(fraction / float(1 << 56)) * (16.0 ** (exponent - 64))` looks like it rounds twice, but 16**k is 2**4k so both scalings are exact powers of two and there is exactly one rounding. 200000 random values, zero disagreements with exact rational arithmetic. It now uses Fraction anyway, to make that single rounding evident and to expose constantValueExact/constantValueRaw for callers that must not lose bits — the float return is inherently lossy for a 56-bit fraction, which no rewrite can change.
- And sdf.py was deliberately NOT translated to C: XCOM-I/sdfpkg.c says so in its header, walking raw System/360 bytes directly as SDFPKG.ASM did, because the caller only ever reads raw bytes. So no native float enters on the C SDF path.
