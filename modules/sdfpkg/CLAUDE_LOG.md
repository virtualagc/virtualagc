- PR #33 opened upstream (ColanderCombo/nsts-sdl-dps): fcmcmp accepts ANY negative exception marker, not only -1. The tool no longer knows what a kind means; an exceptions file declares its own with "# -n = text" comments, used verbatim in the report, falling back to "known discrepancy of type -n" when undeclared. Markers are decimal, values hex, so the two cannot be confused. Verified against the real 46291-entry exceptions-S2-full.txt.
- Two earlier drafts were wrong in the same way: they hard-coded -2 as a second special case (first as literal branches, then as a table of known markers) instead of opening the marker up. The user's point: as long as we are spending a PR, make it accept any negative value, and put the human-readable meanings in the exceptions FILE rather than the tool. That is strictly better — a new kind now costs no upstream change at all.
- The semantics, for the record: -1 = believed to be an undocumented change between OI34.06 and OI34.07, FCOS especially, on good evidence but unproved. -2 = believed to be a bug in the ORIGINAL compiler, such as bad IBM hex float encoding, also unproved. They are not interchangeable: -1 says the difference would go away given the right source, -2 says it would not because our output is right and the dump is wrong.
