### [2026-08-02] Target: [familiarization-findings.md]
- Both remaining latent defects fixed, and fixing them turned up four more in the same never-executed stretch of HALINCL/VMEM3.py.
- The MISC family (GET_MISCF/SET_MISCF/GET_MISCH/SET_MISCH/GET_MISCB/SET_MISCB) now reaches its datum with COREWORD/COREHALFWORD/COREBYTE over the core address LOC_MISC returns, instead of doing NODE_F(0) on a Python list. SET_MISCF's v2.ODF (no such name; VMEM2 defines only MODF) corrected. SET_MISCH keeps the XPL's vestigial OLD_VALUE parameter but defaults it, since XPL had no other way to declare a procedure-level local. LOC_MISC's `OFFSET / VMEM_PAGE_SIZE` was Python float division where XPL's FIXED division truncates, so SHL() had nothing it could shift.
- MISC_ALLOCATE marked a multi-page table with `| 0x80000000`, which makes a 32-bit FIXED negative but leaves a Python int positive, so LOC_MISC took the single-page branch and added the whole byte offset to one page's offset field. Now coerced to signed 32-bit.
- PTR_LOCATE, all in code no compile had reached: `BAD_PTR;` twice as a bare name rather than a call, so an invalid pointer was diagnosed nowhere; `VMEM_TOTAL_PAGES` unqualified (NameError); `EXIT;` bare; `d` never imported, so the CLASS_BI diagnostics could not have been issued anyway; `global PREV_COUNT` misspelling PREV_CNT; and SET_INDEX declaring `global PREV_CNT, CUR_INDEX` where CUR_NDX was meant, so CUR_NDX stayed -1 and PAGING_STRATEGY always reported error 700.
- The structural one: the XPL's `GO TO LOC_COMMON1` leaves the new-page branch and lands inside the *other* branch's `IF CUR_NDX = -1 THEN DO`, just past the FILE read. The port set `goto` and then simply fell out of the if/else, so a newly created page was never recorded in VMEM_PAGE_TO_NDX or VMEM_PAD_PAGE and VMEM_PAD_CNT was not updated. Consequence: the next reference to that page took the reload path and PAGING_STRATEGY eventually tried to write a page out to page number -1. The label's body is now lifted out below both branches, which is where all three paths converge in the XPL.
- GET_CELL's page-search loop was missing the exit that `GO TO GET_SPACE` performs, so it ran to its last iteration and handed PTR_LOCATE the wrong page's PAGE/AVAIL_SIZE -- PAGE 0 with a negative AVAIL_SIZE, i.e. an offset past the end of the page. This one was *not* latent: it happens on 029-DATATYPES with SIMULATING on. It went unnoticed only because BAD_PTR was a no-op and because normalize() treats a core address flatly, so the malformed pointer happened to land on the right byte anyway. Making BAD_PTR a real call is what exposed it; the compile aborted with BI701 until the loop was fixed.
- DECOMPRE.py ported from DECOMPRE.xpl; NEXT_RECORD now imports DECOMPRESS instead of calling a nonexistent g.DECOMPRESS. IN_REC_PTR is module-level, XPL locals being static, which is what lets one call resume where the last stopped. The duplicate-character loop is written out because XPL's `DO OUT_REC_PTR = OUT_REC_PTR TO OUT_REC_PTR + (CNTL_BYTE & '3F') + 1` evaluates its limit once and leaves the variable one past it.
- Verified by round trip against a compressor written to the same format: six cards including blank runs, literal runs, a 66-character repeat, an all-blank card and a run straddling a record boundary. The EOF branch had to be driven directly, for the reason below.
- Porting DECOMPRE is necessary but not sufficient for compressed source, and the docstring now says so. A compressed record is binary, but the port carries a record as a Python str and recovers bytes with BYTE(), i.e. asciiToEbcdic[ord(c)] -- which has no preimage for 130 of the 256 values, 0xFF (the EOF control byte) among them. Reading compressed source also wants the input path to carry bytes rather than characters, which is a change to the I/O model, not to DECOMPRE.
- Regression: 98 sources byte-identical to the pre-change baseline, identical statuses, empty stderr. New probes: 30 MISC checks, 11 DECOMPRESS checks. tests/runall.sh 13/13, cmem 78, sdfpkg 3451.

### [2026-08-02] Target: [sdfpkg-rationale.md]
- DEFERRED WORK, agreed with the user 2026-08-02: SPACELIB errors are skipped rather than fixed, and must be come back to. SPACELIB is linked into every pass and can abend with BI002 (bug in the space-management system), BI003 (the same with too little space left to describe it), BI004 (too many such errors) or BI010 (yoyoing -- try a larger region), all severity 3 and all naming "SPACE MANAGEMENT". The user reports having seen several kinds and never having corrected any. First one met in practice: APPLSRC/RVMCON.hal of OI340600, "BI002 SEVERITY 3 BUG IN SPACE MANAGEMENT SYSTEM ->->NON COMMON RECORD AT LINK, DOPE=4448", raised by HALSFC-PASS3 on a file PASS1 compiled with zero errors.
- The deferred work is on the C side only. Correction from the user 2026-08-02: since HAL_S_FC.py has no memory model at all, and SPACELIB exists to manage allocation and garbage collection within one, SPACELIB functionality is *meaningless* in the Python port. What references survive there are only because deleting them was more trouble than leaving them. So the Python side wants deletion, not repair, and removing the SDF path's SPACELIB calls from INCSDF.py -- the paging-area augment, the FORFCB/PGING allocate-and-free pairs, the SYM_TAB capacity reservation, each replaced by a comment quoting the XPL it stood in for -- was the correct treatment rather than a compromise.
- What HALINCL/SPACELIB.py still does is not space management. RECORD_CONSTANT appends Python objects to a list (bytearrays of VMEM_PAGE_SIZE for VMEMREC, class instances for FOR_ATOMS and LIT_PG, None otherwise), RECORD_ALLOC returns len(), and RECORD_USED is already a no-op. Only the VMEMREC allocation is load-bearing, VMEM3 taking VMEM_PAD_ADDR[I] from it. Whoever eventually deletes the rest should keep that in mind.
