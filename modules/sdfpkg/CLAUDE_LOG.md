### [2026-08-02] Target: [familiarization-findings.md]
- Applied all of the above fixes, plus the SDF enablement work. Two further bugs surfaced while verifying them: (a) `STAB_VAR` is called at SYNTHESI.py:1890 and :4175 but was never imported there (`NameError` on 21 of 99 test sources once SIMULATING is on); (b) STREAM.py's `D DEVICE CHANNEL=n` loop relied on the XPL rule that `DO I = a TO b` leaves `I` at `b+1`, whereas Python's `for` leaves it at `b`, so a one-digit channel — the only legal kind — always took the NO_CHAN exit and reported XD3. OUTPUTWR.py already compensates for that same idiom in three places (`I += 1  # Terminal value of for-loop differs...`); STREAM was the only place that missed it. An AST sweep for other loop variables read after the loop found no further genuine instances.
- New `--sdf` switch (g.py, default False) replaces the hardcoded `g.SIMULATING = 0` in INITIALI.py. Without it behaviour is bit-for-bit what it was; with it, `SIMULATING = (OPTIONS_CODE & 0x800) != 0` as in the XPL. Note 0x800 is the TABLES option, which is on by default, so `--sdf` alone is enough to exercise the path. It deliberately does NOT gate INCLUDE-from-SDF (HALINCL/INCSDF.py), which is reached only when the HAL/S source asks for it.
- STABHDR.py ported for real (was a docstring stub). Needed new `COREBYTE`/`COREHALFWORD`/`COREWORD` helpers in HALINCL/VMEM3.py: XPL reached virtual-memory cells through BASED variables, i.e. pointers, so `NODE_H(13) = X` becomes `COREHALFWORD(NODE_H + 2*13, X)` over the integer "core address" that GET_CELL()/LOCATE() return. The dope-vector idioms `COREWORD(ADDR(NODE_H)) = COREWORD(ADDR(NODE_H)) + 4` and `COREWORD(ADDR(NODE_F)) = ADDR(NODE_H(0))` become `NODE_H += 4` and `NODE_F = NODE_H`. The 4 INLINE statements per SRN block are an `MVC` of 8 bytes of SRN text into the cell at offset SRN_INX.
- FINISH_MACRO_TEXT (HALINCL/FINISHMA.py) also had to be finished: its `SIMULATING > 0` branch wrote the cell header to Python locals `l.NODE_F0`/`l.NODE_F1` instead of to virtual memory, and handed `MOVE()` a byte *value* where the XPL passed `ADDR(MACRO_TEXT(n))`. Since MACRO_TEXTS is a list of one-byte objects rather than a contiguous run, the copy is spelled out byte-at-a-time in a new local `MOVE_MACRO_TEXT()`.
- Still unported / still stubs, deliberately left alone: DECOMPRE.xpl (so `g.DECOMPRESS` in NEXTRECO.py would still fail on compressed source), and SET_BLOCK_SRN (SETBLOCK.py returns immediately, and its `BLOCK_SRN_DATA = GET_CELL(2044, MODF)` is commented out in INITIALI.py). SET_BLOCK_SRN is *not* SIMULATING-gated, so reinstating it would change every compile and wants its own decision. The `GET_MISCF`/`SET_MISCF`/`GET_MISCH`/... family in VMEM3.py is likewise still placeholder code that would raise `TypeError` if called (`NODE_F(0)` on a Python list); the new CORE* helpers are what those want.
- Regression evidence: `HALSFC --test --clean --archive` over all 98 sources in "Source Code/Programming in HAL-S/" plus DEMO.hal and HELLO.hal gives results byte-identical to the pre-change baseline (88 fully clean, the same 11 pre-existing failures, no new ones). Separately, all 99 sources compile identically with and without `--sdf` (99 identical reports, 0 crashes), confirming the SDF path now runs end-to-end without perturbing PASS1 output. A hand-written `D DEVICE CHANNEL=5 PAGED` test now compiles clean and matches HALSFC exactly; before the fixes it gave a spurious XD3, and with a 2-digit channel it died with `TypeError: 'int' object is not callable`.
