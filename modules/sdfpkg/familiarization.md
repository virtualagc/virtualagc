`HAL_S_FC.py` is a partial port to Python of a program called `HAL/S-FC`, which resides in directory ../../yaShuttle/"Source Code"/PASS.REL32V0/. `HAL/S-FC` is a compiler for the computer language HAL/S, and consists of 7 passes, called `PASS1`, `FLO`, `OPT`, `AUX`, `PASS2`, `PASS3`, and `PASS4`.  `HAL_S_FC.py` is specifically a port of `PASS1` to the Python 3 language, and in _almost_ all respects is intended to be a faithful statement-by-statement translation. `HAL/S-FC` is written in an obsolete computer language called XPL/I, usually called just XPL, for which there is no significant online documentation. The language is relatively-easy to understand without documentation, but it has quirks that must be understood, for which I would recommend reading the web page about my own compiler (`XCOM-I.py`) for the language.  `XCOM-I` is locally installed on this computer.  There is a local copy of my web page, and the section of particular interest is at:  ~/Desktop/sandroid.org/public_html/apollo/XPL-I.html#xpli.

The Python port, `HAL_S_FC.py`, has peculiarities with which you need to be familiar as well. Most _global_ variables defined in `HAL/S-FC`, typically in the file PASS1.PROCS/##DRIVER.xpl, are in the `HAL_S_FC.py` file g.py, which is imported into other `HAL_S_FC.py` files as a module, so most global variables from `HAL/S-FC` are in the `g.` namespace in `HAL_S_FC.py`. Other global or "COMMON" variables from `HAL/S-FC` are imported as other namespaces, such as `h.` for HALINCL/COMMON.xpl, `d.` for HALINCL/CERRORS.xpl, and so on.

XPL/I "built-in" functions are (in Python) found in the module xplBuiltins.py, which is generally imported as `from xplBuiltins import *`, so they reside in the general namespace.

In XPL/I, local variables of procedures and the arguments of procedures are _persistent_.  In those cases in which persistence is persistent, the Python port typically puts them into a Python `class`, and then refers locally to that `class` as the namespace `l.`.

`HAL_S_FC.py` has been in use for some time, and works well.  However, there is undoubtedly code in it which has never yet been exercised, and which may still contain errors.  The common causes for errors are these:

- Global variables not in the correct namespace because the prefix `g.` has been omitted, or in which `g.` variables are incorrectly attributed to `l.`, or vice-versa.
- Conditionals (`IF`, `UNTIL`, `WHILE`) in XPL/I use only the _least significant bit_ of expressions being tested, and sometimes a necessary `&1` has been omitted when the test was translated to Python.
- Array indices in XPL/I are enclosed in parentheses, versus brackets in Python, and sometimes parentheses have not been correctly translated to brackets.
- In XPL/I, variables declared as scalars can be used as arrays, or vice-versa.  I.e., regardless of whether or not a variable has been declared as an array or a scalar, `VAR(0)` is equivalent to `VAR`, and `VAR(N)` can be used to access the memory location `N` entries in memory away from `VAR`. This is not true in Python, of course, and the Python translation does not in fact even contain a model of the memory that the original XPL/I relied upon.  So wherever this effect occurs, it has to be mimicked somehow by Python functions rather than Python lists.
- XPL/I allows inline embedding of IBM System/360 machine code, via an `INLINE` statement, and sometimes the Python translation of these small bits of machine code is not entirely accurate.
- `HAL/S-FC` source code makes relatively-infrequent but _significant_ use of `GOTO` statements, which are entirely unsupported in Python. In the Python translation these have not been treated entirely consistently, but the typical technique used to mimic `GOTO` is this:  There is a variable called `goto` which has the value `None` normally, but has the name (as a string) of a commanded `GOTO` otherwise.  By means of `IF` statements, blocks of code are conditionally entered always if `goto == None` or if the target label specified by `goto` exists within the block, but are skipped past otherwise.  That's sufficient for forward references.  For backward references, entire blocks of code may be enclosed in a `WHILE` that is conditional on the value of `goto`.  When the target label is reached `goto` is reset to `None`.
- In XPL/I, a string of hexadecimal numbers enclosed in single quotes is a hexadecimal integer literal.
- XPL/I uses `&`/`|` both as logical operators and as bitwise operators, whereas Python distinguishes `and`/`or` from `&`/`|`, and sometimes the translation hasn't been perfect.
- XPL/I uses `=` as both of what in Python would be `=` or `==`, and sometimes the translation is not perfect.
