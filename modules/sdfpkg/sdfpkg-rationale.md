In the HAL/S language, it is possible to import objects called TEMPLATEs into a HAL/S source-code file, with a syntax like `D INCLUDE TEMPLATE name`.  TEMPLATEs perform a role similar to header files in C, in that they centralize declarations of variables and prototypes of procedures and functions that are in common across multiple HAL/S files.  Unlike C header files, however, HAL/S source-code files which are going to be used as TEMPLATEs must be precompiled (with a `HALSFC` command-line switch like `--parms=TEMPLATE`) and stored in a "template library" (the directory TEMPLIB/ for `HALSFC` or the file TEMPLIB.json for `HAL_S_FC.py`) before use.  The TEMPLATE options can be used safely with all HAL/S source-code files, even those not ever used in `D INCLUDE TEMPLATE name` directives.  The `name` used in these directives is not necessarily the filename of the associated HAL/S source-code file.  Rather, the base name of the file is normalized by removing all underscore characters, and truncating to 6 characters, and then prepending the prefix "@@".  For example, if a file called ABC_DEF_GHI.hal were used to generate a TEMPLATE, the TEMPLATE would appear in the template library as "@@AGCDEF".  The `name` in the `D INCLUDE TEMPLATE name` directive can be _anything_ that normalizes to the same 6 characters following the "@@".  Even though TEMPLATEs in the template library are produced by the compiler, and in that sense they are precompiled, in fact they remain basically just HAL/S source code which has been "compressed" by removal of extraneous blank spaces.

Each HAL/S source-code file that's compiled can have an associated SDF, as created by PASS3 of the compiler.  An SDF is essentially an enhanced symbol table for the HAL/S file.

For original developers in the HAL/S language, using TEMPLATEs proved to have certain drawbacks, one of which is that they increased compilation time dramatically, Because every time a HAL/S file is compiled, all of the TEMPLATEs it includes must also be recompiled essentially from scratch.  Because the only actual use the TEMPLATE has is to add items to the internal symbol table being generated by the compiler, it occurred to people that the SDF held all of the information needed to add that same information to the compiler's symbol table, and that SDF's were already compiled to actual binary, so if SDF's could be used in place of TEMPLATEs, compilation speed could be greatly increased.  Therefore, HAL/S-FC was modified so that when _told_ (via `D INCLUDE TEMPLATE name`) to include a TEMPLATE, it would instead first look for an SDF (stored in an SDF library, and named identically to the TEMPLATE but with the "@@" prefixed replaced by "##") and if the SDF existed it would be imported, falling back on the actual TEMPLATE only if the SDF failed to exist. This subsitution of SDFs for TEMPLATEs is performed by INCSDF.xpl (or supposed to be performed by INCSDF.py in `HAL_S_FC.py`).  This is the capability we are trying to now implement in `HAL_S_FC.py`.

INCSDF.xpl relies upon a large System/360 Basic Assembly Language (BAL) package residing in ../../yaShuttle/"Source Code"/PASS.REL32V0/SDFPKG.ASM.  SDFPKG.ASM is not used directly by INCSDF.xpl, but is instead accessed by the XPL/I built-in `MONITOR` function via `MONITOR(22)`.  `MONITOR(22)` provides several subservices related to virtual memory (`VMEM`) because SDFPKG.ASM depends heavily on virtual memory, and several services related to _searching_ an SDF in several ways. I.e., given a search criterion, it returns the "cell" in the SDF corresponding to that search criterion.  INCSDF then uses the content of that cell to update the compiler's internal symbol table.  Whereas in the original implementation SDFPKG.ASM would search the SDF in place, using `VMEM` to page portions of the SDF in and out of memory as needed, in the Python port, the module `sdf` (assisted by the `cmem` module) is tasked with _parsing_ an entire SDF into a convenient Python representation in memory, in termse of Python lists and dictionaries and datatypes.  The native SDF uses System/360-style datatypes, such as IBM Hex Floating Point, whereas the parsed SDF in Python memory uses native Python datatypes in most cases.  The searches performed by the `sdfpkg` module are performed on this Python-native structure.

The `sdfpkg` module has only been partially completed, and several search types remain to be implemented.

There are a couple of difficulties.  One difficulty is that the page caches used for virtual memory by `cmem` is of a variable size.  The cache is _initialized_ with a selected number of 1680-byte pages, which is fine.  However, two of the `MONITOR(22)` subservices are devoted to growing the page-cache (if the maximum size assigned to it is inadequate) and to shrinking the page-cache (if all the extra pages are no longer needed).  This is very tricky in the Python port, because there is model of memory as such, and the original techniques for allocating/deallocating memory are therefore inapplicable.  My workaround for this, as yet unimplemented, is simply to insure that the initial selection of the maximum page count for the cache is large enough that it never needs to be increased later.

The second difficulty is that the API (for most subservices) for `MONITOR(22)` is `MONITOR(22, mode)`, where `mode` selects the specific subservice.  However, input parameters and output results for the selected subservice are not explicitly passed.  Rather, they in a fixed-size fixed-position section of memory called `COMMTABL`.  Prior to calling `MONITOR(22, mode)`, arguments are shoved into appropriate fields of `COMMTABL`, and after the return from `MONITOR(22)` the output data is extracted from the appropriate fields in `COMMTABL`.  This is problematic because SDFPKG.ASM/`sdfpkg` expects to find `COMMTABL` in memory, but there is no memory model in the Python port.  The workaround is that a _very short_ memory model is created as a `bytearray` object, and `COMMTABL` is kept there.  A second difficulty is that the data in `COMMTABLE` must be in the expected System/360 datatypes, whereas to transfer data in/out of `COMMTABL` for use by the Python port of INCSDF, it must be translated from/to native Python formats.

There is documentation on the format of SDFs and how SDFPKG.ASM relates to `MONITOR(22)` in the documents ~/Desktop/sandroid.org/public_html/apollo/Shuttle/SDFPKG-USERS-GUIDE-29-14.pdf and (in the same directory) HAL-S-FC-SDL-INTERFACE-CONTROL-DOCUMENT.pdf. You may find it more efficient to permanently extract the text from the documents at the outset rather than to continually refer to the PDFs.

The objective after all of those things have been implemented is that INCSDF.py should be able to find the SDF (within the SDF library) corresponding to a requested TEMPLATE, and if found, update the in-memory symbol table according to its contents.

# Implementation record

The objective stated above is met: `HAL_S_FC.py --sdfi=SDFLIB` finds the SDF
corresponding to a requested TEMPLATE and updates the in-memory symbol table
from it.  What follows records how, what had to be fixed along the way, and how
it is known to be right.

## Where the description above is now out of date

  `INCSDF.py` needs only 0, 1, 2, 4, 5, 7, 8, 9 and 13, but `HALSTAT.xpl` uses

  to be ported to C later for `HALSFC`, possibly PASS4, and `HALSTAT`.  The

  rather than avoided.  An augment is honoured when the caller's area abuts the

  replacement for the paged bytes; the two are complementary.  The self-test

  deletes any such leftover.  `modules/sdfpkg` installs the usual way,
  `pip install -e modules/sdfpkg`, or automatically via `pipIt`.
- Two copies of the SDFPKG assembly exist, and the newer one should be used.
  `Source Code/MISCELLANEOUS/` holds "SDFPKG: VERS 2.0, CRAIG W. SCHULENBERG,

  INITIALIZATION DATA TO SDF").  Every difference between the two `SDFPKG.bal`
  files is a CR13079 line.

## There is no reference implementation, so the test is the substitution invariant

`HALSFC-PASS1` contains the entire XCOM-I translation of `INCSDF.xpl` (symbols
`STREAMxINCLUDEuSDF*`, based `SDF_B/H/F`) and honours `--sdfi=SDFLIB`, but its
runtime prints "FYI: MONITOR(22,0,n) not yet implemented" and falls back on the
TEMPLATE.  Verified end to end: `HALSFC --parms=TEMPLATE` on COMPA/COMPB yields
`SDFLIB/##COMPA .sdf` and `TEMPLIB/@@COMPA`, and `HALSFC-PASS1 --sdfi=SDFLIB`
then reports "REL3 SDF ##COMPA  NOT FOUND" and produces a report identical to
the no-SDF run.  So the `--test` oracle that served for the PASS1 fixes is
unavailable here.

The substitute is the *substitution invariant*.  Adding entries to the symbol
table is the only thing a TEMPLATE is for, so SDF-for-TEMPLATE is correct only
if both routes leave the compiler with the same symbol table — which makes the
two routes each other's reference implementation.  `tests/invariant.py` compiles
the same source twice, once with an SDF library present and once without, and
requires `SYM_TAB.json` to agree.  It is self-checking, needs no second
implementation, and will apply unchanged to `HALSFC` once its `MONITOR(22)` is
filled in (it takes `--compiler=`).

Two guards keep it honest.  It requires the `--sdfi` run to report "INCLUDED
FROM SDF" and the other run not to, because an SDF route that quietly fell back
on the template would otherwise agree trivially; and it fails if neither route
compiles cleanly, so that two identical failures cannot masquerade as agreement.

Five differences are exempted, each justified rather than tolerated:

- `SDF_INCL_FLAG`, whose whole purpose is to record that the block came from an
  SDF, so the routes *must* differ.
- `SYM_ADDR`.  PASS1 never assigns addresses, so a TEMPLATE has none to offer,
  whereas an SDF carries the ones its own compilation settled on.  Picking them
  up is a benefit of the SDF route.
- `SYM_LINK1`/`SYM_LINK2` on a block label.  `SET_LABEL` threads these only for
  labels it sees defined in source (`SETLABEL.xpl:110-113`); a block arriving
  from an SDF is entered directly, in the original XPL exactly as here, since
  `INCSDF.xpl` sets those links only inside `ENTER_SDF_TEMPLATE`.
- `SYM_XREF`, an index into the cross-reference table.  Including a TEMPLATE
  inserts source that is itself cross-referenced, so the table is larger and
  every index shifts.  Rather than ignore the field, the *flag bits* of each
  symbol's leading cross-reference entry are compared instead, and those agree.
- `DEFINED_LABEL` on a label declared inside a structure template, one
  direction only.  Checked rather than assumed: `INCSDF.xpl` names
  `DEFINED_LABEL` in exactly one place, line 794, for the compilation unit's own
  block label, and the SDF flag set carries nothing for `SET_SYT_FLAGS` to map
  onto it.  The port's `IN_FLAG`/`OUT_FLAG` tables and all nineteen `SDF_*_FLAG`
  constants match the XPL exactly.

Some INCLUDE forms are *meant* to differ between the routes and so cannot be
checked this way; `tests/directives.py` states their expected outcome outright
instead.  `tests/runall.sh` runs all thirteen cases: seven invariant pairs
(USEA 15 symbols, USEF 7, USEP 8, USEM 10, USELB 10, USER 14, USEAB 24) and six
directive cases (USES, USES2, USEL, USEL2, USEL3, USEL4).

Two notes for anyone adding fixtures.  The template library `HAL_S_FC.py` uses
is `TEMPLIB.json`, not `HALSFC`'s `TEMPLIB/` directory, so it must be built with
`HAL_S_FC.py` itself; the SDF library must be built with `HALSFC`, since only
PASS3 writes an SDF.  And multiplication in HAL/S is juxtaposition, `A B`; `*`
is the cross product and gets you error E4.  `COMP_USE.hal`, the obvious
starting fixture, errors in both compilers and is no use as a baseline.

## What had to be fixed in the modules

**`cmem`.**  `abend()` used `os._exit`, discarding whatever the caller had
buffered — which is why the self-test looked as though it printed nothing but
two Abend lines; it now flushes first.  `_resolveSdfName()` accepts an SDF name
with or without the trailing blanks of the 8-character `SDFNAM` field and
canonicalizes on whichever spelling exists on disk, PASS3 writing
`"##COMPA .sdf"` while callers routinely build the name unpadded.  Modes 2 and 3
implemented as described above.  SELECT (auto-select) implemented for modes 5
and 7–17.

The RELS/ABEND5 fidelity gap is closed.  The codes come from `SDFPKG.bal`'s
abend table: ABEND4 = 4003 "TOO MANY RESERVES FOR ONE PAGE"
(`CH R1,=X'7FFF' / BE ABEND4`), ABEND5 = 4004 "TOO MANY RELEASES FOR ONE PAGE"
(`LTR R1,R1 / BZ ABEND5`).  `_padDecResucntIfPositive` had been silently
clamping, which would let a page the caller still believes is pinned be evicted
underneath it; it is now `_padDecResucnt` and abends.  Reserve saturates and
abends rather than wrapping a halfword round to 0.  `_applyDisposition` was also
reordered to `SETDISPS`'s CHKMODF/CHKRELS/CHKRESV — releasing before reserving
matters when both bits are set at once, since otherwise an unreserved page is
incremented and decremented back to 0 without complaint.

One bug here was subtle enough to be worth recording in full.  Including a
second COMPOOL re-read the *first* one's pages, so the second import reported
"COMPA IS A DUPLICATE LABEL".  `INCSDF` supplies the Paging Area Directory out
of its own static memory model, so the PAD outlives any one `cmem` instance —
and `MONITOR(22,0)` builds a fresh `cmem` per include.  `cmem` hands out SDF ids
from 1 each time, so an inherited PAD entry for the old SDF was mistaken for a
page of the newly selected one and `_findCachedPage` returned it.  `_mode0` now
marks every PAD entry free, which is what initializing means.

**`sdf`.**  `convertEbcdicToAscii` was missing its `@staticmethod`, so
`anInstance.convertEbcdicToAscii(x)` bound the instance to the `bytes`
parameter.  That was the cause of `sdfpkg` mode 8's `TypeError`.

**`sdfpkg`.**  `disp` was extracted *after* `mode` had already been masked to 16
bits, so it was always 0 and no disposition ever reached `cmem`; and the
follow-up call passed the disposition as the *commtabl* argument.  Modes 8, 9
and 10 were repaired and 11 through 17 implemented.  The former silent `return`
stubs were the worst of it: a stub left the previous call's COMMTABL values in
place, so it read as success.  Mode 4 now invalidates the parse, so selecting a
different SDF re-parses; mode 13 keeps (name, symbol number) so that
"successive mode 13 calls are legal" resumes rather than repeating.

Block, symbol and statement numbers in an SDF are all **1-based**.  `##COMPA`'s
Directory Root Cell reports `indexOfCompilationUnitBlockDataCell = 1` for its
sole block, whose own `blockIndexNumberInBlockIndexTable` is also 1, and it
lives at `blockIndexTable[0]`.  Modes 8, 11 and 15 had been indexing the table
directly; the symptom was `BLK_TYPE` reading 0 (UNDEFINED) instead of 4
(COMPOOL) and `#BLK_SYMBS` reading 18524 instead of 11.

`BLKNAM` and `SYMBNAM` are fixed 32-byte COMMTABL fields and callers write only
the name's own characters, so "IA" written over a previous "ASTRUCTURE" leaves
"IATRUCTURE" behind.  The length field is the only thing that says where the
name ends, which is why CHKMATCH loads `SYMBNLEN` before comparing.  Modes 11,
12 and 13 now truncate to `BLKNLEN`/`SYMBNLEN` via `_inputName()`.  The
self-test had been setting the name fields without the length fields, i.e. not
as a real caller does, and was corrected too.

CHKMATCH is transcribed from `SDFPKG.ASM/SDFPKG.bal` rather than from the
User's Guide, because the two disagree.  The guide says "If EQUATE EXTERNAL,
unqualified STRUCTURE or TEMPLATE, then skip symbol"; the assembly's
`TM FLAG1,X'03' / BC 5,SYMFOUND` *accepts* when either of those two flag bits is
set — mask 5 = CC1|CC3 = "some or all of the tested bits are set".  Only the
EQUATE EXTERNAL case, class 2 type 8, is a skip.  The assembly is what ran, so
it wins.  CHKMATCH/CHKTYPE is byte-for-byte identical in both copies of the
assembly (only the columns 73–80 sequence numbers differ), so this is a real
disagreement and not a version artifact.  `DIAGNSTC.MACLIB/SYMBDC.bal` confirms
FLAG1 is at offset 8, i.e. the most significant byte of the fullword `sdf.py`
calls `flagBits`.

Mode 18 needed the same treatment and had been got wrong.  The User's Guide
(SFOC-PASS0092, 02/08/99) documents mode 18 as "Deselect an SDF (FSWAT C version
only)"; CR13079, three months later, gives the assembly a mode 18 of its own —
`B INITDATA  FIND INIT DATA AT GIVEN #` — gated by `CLI SDFVERS+1,33 / BH
NEWCHECK`, so only for SDFs newer than version 33.  Both statements are true,
for different targets.  `sdfpkg` implements the assembly's mode 18 and exposes
deselect as a `deselect()` method instead.  INITDATA runs the whole mode 9 path
and then recomputes the address: `L R4,SYMBLEN / N R4,=X'00FFFFFF'` takes
RELADDR from the Symbol Data Cell, doubles it (halfwords to bytes) and adds it
to DINITPTR (Directory Root Cell offset 156, which `sdf.py` calls
`pInitializationTable`), normalized on 1680.  The assembly reads those three
bytes unconditionally, whereas `sdf.py` records
`relativeMemoryAddressOfSymbol` only for the classes where they really are an
address — for a REPLACE label they are a byte count, and for other class 2/3
symbols a statement number — so the port reads the raw bytes rather than the
parsed field.

`sdfpkg.py --test [--sdflib=DIR] [--sdf=NAME]` drives every mode against
whatever SDFs it is given and checks each answer against the independently
parsed representation of the same file, rather than checking a binary fixture
into the tree.  3451 checks pass over the 26 SDFs in
`yaShuttle/yaHALMAT2/SDFLIB`, 0 failures.  `cmem`'s own suite is 78 passing.

## Wiring MONITOR(22) up

`MONITOR(22)` in `xplBuiltins.py` was a bare `pass`.  The new `MONITOR22()`
there builds the `sdfpkg` instance on mode 0 and refreshes the Python-dictionary
mirror of COMMTABL from the memory model before every call — the memory model is
what `INCSDF` actually writes into, so it, and not the dictionary, is
authoritative.  `INCSDF.py` lends its `bytearray` via
`registerSdfMemoryModel()`; the registration has to go that way round because
`INCSDF` imports `xplBuiltins`.  Its memory model also gained a fourth area for
the PAD, 16 bytes per page, which had been overlooked.  All 19 fields of
`INCSDF.py`'s `COMMTABL_BYTE`/`HALFWORD`/`FULLWORD(n)` accessors were checked
mechanically against `cmem`'s `OFF_*` constants and land on exactly the same
offsets.

The switch is `--sdfi=DIRECTORY`, deliberately the same name, meaning and
default as `HALSFC-PASS1`'s, so that the two compilers can eventually be driven
identically.  With no directory given, no SDFs are read and `INCLUDE_SDF`
reports "not found", which is exactly the old behaviour.  `--sdfpkg` survives as
a synonym for `--sdfi=SDFLIB`.

## Rehabilitating INCSDF.py

`INCSDF.py` had never executed.  An AST scan found 78 bare references to
COMMTABL and SDF accessor functions used without parentheses
(`SDF_B_base = SDFPKG_LOC_ADDR`, `if SDF_SYMB_TYPE > 8`, `LOCATE_SDF_ROOT;`,
…): 72 became calls and 6 became setter calls, applied in two AST passes so that
an assignment target and a bare reference on the same line could not corrupt
each other.  Beyond those:

- `COMMTABL_HALFWORD = COMMTABL_base` and its two siblings were assigning to the
  accessor *functions* rather than to the `_base` variables.
- Seven nested procedures needed `nonlocal` for the 12 variables they share with
  `INCLUDE_SDF`, which in the XPL are simply procedure-level declarations
  (verified that none of them re-declares its own).
- Eight sequence-valued names were being called rather than subscripted —
  `REASON(I)`, `SOURCE_FLAG(I)`, `FATHER(LEVEL)`, and so on.
- `SCOPEp` and `MAX_SCOPEp` were unqualified and so became locals, and
  `MAX_SCOPEp` is a COMM-backed accessor needing a call; likewise
  `g.FIRST_FREE` and `g.NDECSY`.

SPACELIB is gone from the SDF path.  The paging-area augment, the
`FORFCB`/`PGING` allocate-and-free pairs and the `SYM_TAB` capacity reservation
are all no-ops against a static memory model and a Python list, each replaced by
a comment quoting the XPL it stands in for.  The one remaining
`SDFPKG_CRETURN() == 12` (FCB area exhausted) abends rather than trying to
extend an area that cannot grow.

Several bugs in it were interesting rather than mechanical:

- **`SDF_H()` and `SDF_F()` did not sign-extend.**  `BASED SDF_H BIT(16)`
  up-converts to FIXED *with sign extension*, whereas the port returned an
  unsigned 0..65535.  `ENTER_SDF_TEMPLATE` recognizes the end of a structure
  level by `IF SDF_SYMB_LINK2 < 0`, which could therefore never be true, so the
  template walk ran off the end of the declare chain and swallowed every
  remaining symbol in the compool — the loop appeared to run once and stop.
  This was the single biggest bug.  `SDF_B()` is BIT(8) and stays unsigned,
  since BIT(1) through BIT(15) up-convert positive.
- **`ENTER_COMSUB_ARGS`'s two loops were inverted.**  Both are
  `DO UNTIL CUR_SYMBOL = LAST_COMSUB_SYMB`, which repeats while the condition is
  *false*; the port had `while first or CUR_SYMBOL == LAST_COMSUB_SYMB`, so each
  ran exactly once.  A two-argument FUNCTION therefore imported only its first
  parameter, and with the wrong flags.  The `DO UNTIL LEVEL < 0` in
  `ENTER_SDF_TEMPLATE` had been rendered correctly as `while LEVEL >= 0`, so
  this was not a systematic misreading; these two were simply wrong, and they
  were the only three `DO UNTIL`s in the module.
- **`MAKESTRING` returned a descriptor, not a string.**  An XPL string
  descriptor holds the length *minus one* in its top byte and the address in the
  low three, and an all-zero descriptor is the special case for an empty string,
  which occupies no data storage.  `COMPILER = SDF_ROOT_COMPILER` was therefore
  comparing a Python string against an integer and could never be true.
  `MAKESTRING` now reads the bytes and converts from EBCDIC, returning `""` for
  a zero length.  Its inverse, `STRING_AT()`, was needed for
  `SDF_REPL_ARG_NAME`: `STRING(SDFPKG_LOC_ADDR+SDF_F(1+i))` passes
  `xplBuiltins`' `STRING()` a descriptor rather than a string.  The relative
  address is relocated by adding `SDFPKG_LOC_ADDR` before decoding, and the
  length in the top byte survives the addition because addresses are 24-bit.
- **The `MOVE` calls addressed the wrong memory model.**  `HALINCL/VMEM3.py`'s
  `MOVE` addresses the compiler's own virtual memory on FILE6, so it was quietly
  scribbling on the wrong buffer.  Replaced by local `MOVE_TEXT_TO` (a string
  into a COMMTABL field) and `MOVE_MACRO_TEXT_FROM` (SDF bytes into the
  `MACRO_TEXTS` list).
- `RVL_STRING` was added for `STRING("01000000"|ADDR(REV))`, which reinterprets
  the halfword REV as the two EBCDIC characters SELECT takes from the PDS
  directory entry.  A library of plain files has no such entry, so `cmem`'s mode
  4 reports 0 — what GETRVL reports when there is no revision level — and that
  prints as "RVL 00".

## Coverage

Every INCLUDE form has been exercised:

- Plain `D INCLUDE TEMPLATE name`, scalars, a bit string, a character string and
  all four members of a structure — USEA, 15 symbols identical either way.
- Comsubs: a FUNCTION with two parameters (USEF) and a PROCEDURE with an ASSIGN
  parameter (USEP).
- REPLACE macros, three of them and one parameterized, all actually expanded by
  the user program (USEM).
- Multiple compools in one compilation (USEAB, 24 symbols).
- The partial list, `D INCLUDE TEMPLATE name: a, b, c;` (USEL and friends).  This
  cannot be checked by the invariant: it is handled entirely inside
  `INCLUDE_SDF`, and when no SDF is found `PATCH_INCLUDE` falls through to
  `FINDER` and includes the whole template with the list ignored, so the two
  routes are meant to differ.  `directives.py` states the expected symbol table
  outright and adds two negative cases — referring to an unlisted symbol must
  fail as undeclared, or the list is not restricting anything, and naming
  something absent must give XI7.
- `ENTER_SDF_LABEL`, i.e. symbol class 5, "Template label", with types
  PROGRAM/PROCEDURE/FUNCTION/COMPOOL/TASK.  Reaching it needs a structure
  template with a *label* member; the syntax is production 363,
  `<NAME ID> ::= <IDENTIFIER> NAME`, so `1 PROG NAME PROGRAM` inside a
  `STRUCTURE`.  `NAME PROGRAM` and `NAME TASK` compile; `NAME PROCEDURE` and
  `NAME FUNCTION` do not, presumably wanting parameter specs.  COMPL/USELB
  produce class 5 type 1 and class 5 type 5 symbols.
- `D INCLUDE SDF name`, which has no template fallback — `PATCH_INCLUDE` returns
  as soon as `INCLUDE_SDF` is done.  A present SDF imports the whole compool; an
  absent one gives XI10 "REL3 SDF ##NOSUCH NOT FOUND IN SDF LIBRARY" with no
  fall-through, which the test asserts by requiring "INCLUDED FROM TEMPLATE" to
  be absent.
- `D INCLUDE TEMPLATE name REMOTE`, which sets `REMOTE_FLAG` on the compool's
  variables and passes the invariant at 14 symbols.

## Porting `sdfpkg` to C

`MONITOR(22)` is no longer a stub.  `sdfpkg` lives in the XCOM-I runtime
library, as `XCOM-I/sdfpkg.{c,h}`, because the C that XCOM-I emits from the
XPL/I cannot be edited and `MONITOR(22)` is a runtime service.  The master copy
is XCOM-I's; the copies that turn up in `PASS1.PROCS/PASS1.build/` are
overwritten on every build and must never be edited.  `XCOM-I.py`'s
framework-copy list gained the two files and `Makefile.template` already globs
`*.c`, so nothing else needed changing to get them compiled.

`runtimeC.c`'s `MONITOR22`/`MONITOR22A` now call `sdfpkgService`/
`sdfpkgInitialize`, short-circuiting to the old return value when no `--sdfi`
was given, so a compilation that does not ask for SDFs behaves exactly as
before.  `ebcdicToAscii` had to lose its `static`, `SDFNAM` in COMMTABL being
EBCDIC like everything else in the XPL/I program's memory.

The C walks the SDF's raw System/360 bytes directly, as `SDFPKG.ASM` did, rather
than porting `sdf.py`'s parser to serve as a search index.  The caller only ever
reads raw bytes at the returned `ADDR`, so the index bought nothing in C.
Anything not implemented abends by name rather than returning quietly: a silent
stub leaves the previous call's COMMTABL values in place and therefore reads as
success, which is exactly how the Python's unimplemented modes once managed to
look as though they worked.

One bug is worth recording, found the moment it first ran.  Modes 8 and 9 must
report far more than `PNTR`/`ADDR`: mode 9 also sets `SYMBNAM`, `SYMBNLEN` and
`BLKNO`, and mode 8 sets `BLKNAM`, `BLKNLEN` and `CSECTNAM`, because `INCSDF`
reads the located symbol's *name* back out of COMMTABL in order to enter it.
Returning only the pointer gave "PM2 DUPLICATE DEFINITION OF STRUCTURE TEMPLATE"
as `INCSDF` worked from whatever the previous call had left in the field.

The RVL divergence turned out to be mine, in the Python.  `BLKNO` carries the
revision level as two EBCDIC characters, not as a number, so "absent" is the
characters `00` and not binary zero — which the XPL's
`STRING("01000000"|ADDR(REV))` renders as two NULs.  `cmem`'s mode 4 now reports
0xF0F0 in both implementations and `INCSDF.py`'s `RVL_STRING` is a plain decoder
rather than a special case.

With both compilers importing SDFs, `HALSFC --test --sdfi=SDFLIB` reports
`pass1.rpt`, `FILE1.bin` (HALMAT), `FILE3.bin` (IC), literals and `LISTING2` all
identical between `HALSFC-PASS1` and `HAL_S_FC.py` on 10 of the 12 `tests/`
fixtures.  The other two, USEL2 and USEL3, are negative cases whose expected
DU1/XI7 errors abort HALSFC before the cross-comparison runs; the C produces
exactly those errors.

This also disposes of `compilePASS.md`'s point 11 entirely.  The concern was
that the C listing a whole TEMPLATE while the Python listed none would make the
reports incomparable — some 4000 lines on `CSDMDT.hal`.  With the C importing
SDFs too, neither lists anything and no report-filter surgery is needed.

## Determining which files belong to PASS

`OI340600` holds auxiliary code as well as PASS, and `compilePASS` originally
compiled every `.hal` in `APPLSRC/` and `SSSRC/` regardless.  (`INCL80/` holds
HAL/S that is not a compilation unit at all — included whole by
`D INCLUDE name`, no TEMPLATE keyword — and is never compiled directly.)

Membership comes from `PFS/mafgen/csects-*.json`, the CSECT indexes per
configuration, distilled from the `DASS_*.ASC` disassemblies.  The method that
works, from the SDL ICD (USA001556) pp. 163–164: every CSECT name is two
characters of type followed by the six-character HAL/S compilation-unit name —
`$0` PROGRAM, `$1`–`$F` task, `#C` COMSUB, *an* internal procedure, *aa* library
routine, `@c` stack, `#D` DECLARE data, `#P` COMPOOL data, `#Z`/`#Q`/`#0`/`#E`/
`#L`/`#X` the ZCON and special data sections, `##` SDF, `@@` TEMPLATE.  So strip
the two-character prefix from every CSECT in the indexes and keep the names: a
unit is in PASS if a CSECT of *any* type was emitted for it.  3859 CSECTs reduce
to 1654 distinct unit names against 1167 source files, which is the right shape
since one file can hold several units, and the surplus is library and assembly
CSECTs — making the test permissive in the safe direction.

`compilePASS` consults the indexes (`--csects=D`, `--no-csects` to disable) and
reports "Not part of PASS, skipping" instead of compiling.  Membership is the
union of all eight configurations.

An earlier attempt tested `#P` plus the name, which is only the COMPOOL *data*
convention and so rejected every PROGRAM — excluding 717 of 1167 files.  Any
conclusion resting on that heuristic, including an earlier claim that 44 of 60
failures were outside PASS, is withdrawn.  The evidence had been on screen and
was misread: RVMCON's own SDF gives its CSECTs as `#PCRATE`/`#PCRCCOT`/
`#PCRDCIL`, none of them `#PRVMCON`.  The corrected method is right on the cases
that exposed the bug — RVMCON, CDR06D, DKFCM8 and CRATE all in PASS; CS4IX3 out
while CS2IX3 is in, so the CS2/CS4 split survives and now has real evidence
behind it.

## BI002 "NON COMMON RECORD AT LINK"

This was the long one, and it was neither an `INCSDF` bug nor a SPACELIB bug.

`RECORD_LINK` enforces that every record still allocated when it runs is in
COMMON — `_IS_COMMON(CUR)` is `CUR < ADDR(DESCRIPTOR)`, and XCOM-I's
`generateADDR` returns `regions[1][1]`, the top of COMMON, for that.  In PASS1
the boundary is 4196.  Records land in region 1 or region 2 purely on the
`COMMON` attribute, exactly as `generateC.py:367-370` says: `COMMON.xpl`'s five
records are declared `COMMON BASED ... RECORD` and land below the boundary,
while `INCSDF.xpl`'s `PGING`/`FORFCB` and `##DRIVER.xpl`'s `INIT_APGAREA`/
`INIT_AFCBAREA` are plain `BASED` and land above it.  There is no
region-assignment defect; an earlier note claiming one, and claiming that the
discriminator was which file a record is declared in, was wrong — `INIT_*` are
declared in `##DRIVER` and still land in region 2.

The actual defect is in XCOM-I and has nothing to do with SDFs.  `generateC.py`
translated a `RETURN` from the *outermost* XPL scope into
`exitCodeLINK = ...; RECORDuLINK(0);`, and the fall-off-the-end case likewise.
But a top-level RETURN is not a LINK.  The XPL routes deliberately *around*
`CALL RECORD_LINK` on exactly the paths where the COMMON invariant does not
hold.  Both sites now emit `LINK();`, which is all that was ever wanted —
`writeCOMMON` plus `exit(exitCodeLINK)`.  The explicit `CALL RECORD_LINK` sites
are untouched.

The clearest instance is `PASS3.PROCS/##DRIVER.xpl:488-491`:

```
IF NOT_DOWNGRADED THEN RETURN "8";
RECORD_FREE(RVL_SRN);
IF HEX_DUMP_FLAG|SDF_SUMMARY THEN CALL RECORD_LINK;
ELSE RETURN COMMON_RETURN_CODE;
```

The early return leaves `RVL_SRN` allocated on purpose, and `RVL_SRN` is dope
4448 in PASS3 — the exact DOPE in every PASS3 BI002.  PASS1's equivalent is
`ALMOST_DISASTER` falling through `MAX_SEVERITY=4; GOTO ENDITNOW;` to its
`RETURN SHL(MAX_SEVERITY,2)`, with `INIT_APGAREA` (4336) still up.

Why it never showed before SDF import: without `--sdfi` the only surviving
records are `COMMON.xpl`'s five, all below the boundary, so the injected audit
passed and looked like nothing.  The SDF path is the first thing to leave a
non-COMMON record allocated at that point, which is why the bug reads as an SDF
regression and is not one.

The same defect is GitHub issue #1274, and it is fixed.  End to end there:
`DMC_NEW_DISPLAY` missing from the include library gives XI3 cascading into 37
DU1 and more; error #99 is BI106 "TOO MANY ERRORS; COMPILATION ABORTED" at
severity 4; severity 4 routes through a PASS1 disaster label that bypasses
`PRINT_SUMMARY` (confirmed — no symbol-table dump in the report);
`PRINTSUM.xpl:138` is the only `RECORD_FREE(OUTER_REF_TABLE)` in PASS1; and
`OUTER_REF_TABLE` is a non-COMMON BASED record at dope 4448, the exact DOPE the
issue reports.  Both files it names now abandon cleanly.  The error count
matters only as one way of reaching a disaster label.

Wrong turns taken along the way, recorded so they are not repeated: `PGING` is
*not* the leaked record and balances 6 allocations against 6 frees; page
thrashing was a theory and eviction logging showed zero evictions;
`INIT_APGAREA` and `INIT_AFCBAREA` *are* freed, in `PRINTSUM.xpl:133-134`.

## Return codes

Every XPL return in the seven compiled passes is a multiple of 4 —
`SHL(MAX_SEVERITY,2)`, or `COMMON_RETURN_CODE` which is only ever assigned the
same, or a literal 0/`"8"`/16/20.  So 4 means warnings, and the compiler's own
rule for viability is `MAX_SEVERITY < 2`: PASS1 chains to the next pass on
exactly that test.  HALSFC aborted on any nonzero, which turned OPT's severity-1
ZO3 into a hard failure and, worse, skipped PASS3 so that no SDF was written for
dependents to include.  `passFailed()` now tolerates rc < 8 at those seven sites
and checks the wait-status low byte for a signal.  `HAL_S_FC.py`'s check stays a
plain test against zero: the Python port has no such convention, its `EXIT()`
being a bare `sys.exit(1)`.

That was only safe once the C side moved out of the severity ladder.  `abend()`
exited 1, from 105 call sites, so rc < 8 would have read every runtime panic as
success.  XCOM-I now abends with 255 (`EXIT_ABEND`) and HALSFC reserves 240–254
for its own diagnoses — 240 pass failed, 241 usage, 242 environment.  For anyone
tempted to spread these further apart: a process exit status is 8 bits, so 256
and its multiples truncate to 0 and read as success.  Verified — C `exit(1000)`
is observed as 232.

`--auto-x1` has been removed from `compilePASS` entirely.  The compiler needed
modifications to support it, so it cannot be historical; it was saving the
*unoptimized* object (ARYMFBUS 2240 bytes against 2160 optimized); and it cannot
succeed on the 19 files carrying `D DOWNGRADE ZO3`, since disabling OPT leaves
those directives unused, PASS2 sets `NOT_DOWNGRADED` and PASS3 returns 8.

`D DOWNGRADE` itself was investigated and is *not* broken.  A matched downgrade
sets SEVERITY 0 before `CERRORS.xpl`'s CR12416 block, so `SEVERITY_ONE` never
gets set and PASS2 returns 0.  The natural experiment: GCMGCS 7/7, GMNLSF 4/4,
GMYRGM 2/2 and VNSNWSCY 1/1 downgraded all reached PASS3, while GCYDBA 8/22 and
GMHACP 10/44 did not.  Directives attach correctly — GCYDBA's three fire at
exactly three statements (59, 60, 98) and the un-downgraded ZO3s are at 57, 58,
107 and 112, which have no directive.  74 of the 93 ZO3 files have no directive
anywhere, so downgrades could never have helped them.

## COMMON could not represent a heap with free blocks

The `LINK()` change above exposed this.  `writeCOMMON` dumps raw bytes only for
0..`ROOT_BASED`−1 (1344 bytes, highest 0x53F) and otherwise serialises declared
symbols.  A free block's eight-byte header — size at B−4, link at B — is
neither, and `runtimeC.c` had no notion of `FIRSTBLOCK` at all.  `FIRSTBLOCK`
was written as a scalar pointing at a header that never crossed, so the next
pass walked uninitialised memory and `_FREEBLOCK_CHECK` correctly abended with
"RECORD HAS WRONG SIZE".

It stayed hidden for years because `RECORD_LINK` squashes the heap before
linking, leaving `FIRSTBLOCK` at 0; only a program writing COMMON *without*
`RECORD_LINK` — PASS2 when `MAX_SEVERITY` is nonzero — can hand over a non-empty
list.  Proved by A/B on identical input: PASS3 exits 0 on the old squashed
COMMON and abends on the new unsquashed one.

`writeFreeBlocksCOMMON` now walks `FIRSTBLOCK` and emits a `%` record per block;
`readCOMMON` restores the header and lowers `freelimit` past the block's bottom
at B−size+4, as it already does per record.  A distinct record type rather than
raw `@` bytes precisely so that the `freelimit` adjustment can happen — without
it the walk fails its *final* size check instead of its first.  Inert where
`lookupVariable("FIRSTBLOCK")` returns NULL.  Self-check on ARYMFBUS: blocks of
0x2920 and 0xF8 sum to 0x2A18, exactly the `FREEBYTES` PASS2 recorded.
Normalising the heap before writing would have been equally legitimate, since
the passes only care that valid data arrived; carrying the blocks was chosen so
that COMMON can express a legal heap state rather than merely avoid one.

The gz COMMON format is same-pass-only and cannot substitute.  It is a raw
image, so it carries PASS2's variables at PASS2's addresses, and PASS3's layout
differs (`FREE_POINT` 0x0132CE against 0x008C47).  Tested: "UNAUTHORIZED THEFT
FROM FREE STRING AREA, WAS=469784672".

## `SUBSTR` pads, and it matters

`runtimeC.c`'s `SUBSTR(s, start, length)` returns exactly `length` characters,
blank-padded when the string runs out; `length` is not merely a maximum.  The
comment that recorded this deduced it from LITDUMP, and LITDUMP does not in fact
demonstrate it: `T` is 25 characters and the three documented `LIT1` type codes
slice it at 0, 8 and 16, so eight characters always remain and the short case
never arises there.  Of LITDUMP's other four uses, one is guarded by
`LENGTH(S)>100` and three take the two-argument form.  The fifth is only
*consistent* with padding, and by accident: `DO CASE (LIT1(TEMP) & "3")` masks
the type code but `SUBSTR(T,SHL(LIT1(TEMP),3),8)` does not, and `ARITHLIT.xpl`
shows `LIT1` can be 5, so `SHL(5,3)` is 40 — fifteen characters past the end.
Padding merely conceals that overrun.  (LITDUMP runs only under `DEBUG ¢E`, and
in PASS1, which never sees the type codes above 2 that PASS2 adds later.)

The deduction was wrong but the conclusion was right, which only the corpus
could show.  Removing the padding moved **282 of 907 compilations**: lines such
as `SYT_DUMP`'s `USED BY: CDUV_DUP_COMMAND` lost leading spaces and shifted
left, because a field assembled from a substring of a too-short string came back
short instead of padded.  So the padding stays.

The one case that must *not* pad is an empty string.  PASS4's SDFLIST strips
leading blanks with `DO WHILE SUBSTR(SDF_NAME,0,1) = X1`, and at end of file
`SDF_NAME` is empty; padding there returns a blank, the string never changes,
and the loop spins for ever.  An empty string has no "past the end" to pad out
to, so it now yields an empty result — the single narrowest change that fixes
the hang.

## PASS4, which is SDFLIST

PASS4 runs, for the first time.  `sdfpkg.c` and `.h` are correctly copied into
`PASS4.build` by the framework list, so the build side needed nothing.

Four modes were added to `sdfpkg.c`.  An initial grep for literal
`MONITOR(22,N)` missed two forms — `MONITOR(22,"10000006")` and
`MONITOR(22,ARG)` where `ARG = SHL(FLAGS,28)+5`, i.e. mode numbers carrying
disposition bits in the top nibble.  `SDFPKG.bal:97-115` is the authoritative
dispatcher table: 6 `SETDISPS`, 15 `BLOCK` (block *node* given #), 17 `STMT`
(statement *node*), 18 `INITDATA` (CR13079).  Modes 15/16/17 locate the
index-table entry where 8/9/10 locate the data cell, which is what PASS4 wants
since it walks the index tables directly.  Mode 6 needed no Python reference: it
applies the disposition bits to the page the last locate left addressed, which
`reply()` already routes through `applyDisposition`, and PASS4 uses it with
`DISP_RESV` to pin a block node's page.

A Statement Index Table entry is 12 bytes with SRNs and 4 without, so
`DRC_FLAG_SRN` (bit 0 of the flag field) must be consulted before indexing, and
statement numbers are ISNs which do not start at 1.  Mode 18's RELADDR is read
as CR13079 reads it, a fullword at `SDC_LENGTHOFNAME` masked with 0x00FFFFFF,
because `SYMBLEN` is the byte immediately before the three RELADDR bytes; it is
gated on Phase 3 version > 33, the halfword at VMP 0.

PASS4 emits the complete dump for `##ARYMFB` — directory data, block data,
symbol table and all 108 statements — in 611 `sdfpkg` calls with no abend.

`DUMPSDF.xpl` needed one fix of its own.  `SYM_SORT` is per-SDF scratch that was
never freed, and `MAX_ARRAY`, its high-water index, is an XPL local and
therefore static, so a second SDF met "IN ALLOCATE_SPACE, ALREADY ALLOCATED"
and would have inherited the previous count even had it got past that.  Only the
`ALL` option dumps more than one SDF in a run, which is presumably why this went
unnoticed.  Both are now reset at the point of allocation.

HALSFC's PASS4 invocation had four faults.  `ERRORLIB` was missing from the
argument tuple, leaving five `%s` against four values, so the command would have
raised `TypeError` the moment it ran; it read `COMMON4`, which is PASS3's
*input*, and wrote `COMMON5`, which is PASS3's *output* — now COMMON5 to
COMMON6; and it passed no `--sdfi`, without which `MONITOR22` short-circuits to
a failure return on every call.  `pass4 = False` is left as the switch to throw.

SDFLIST is not a separate program and needs no build of its own.
`TOOLS.COMPILER.CLIST/SDFLIST` runs `PROGRAM(...PASS4.OBJ)` with PARM `TABLST`
and the SDF name written to SYSIN.  The equivalent here is

```
HALSFC-PASS4 --pdsi=5,ERRORLIB --ddi=0,names.txt --sdfi=SDFLIB --parm="TABLST"
```

with one SDF name per line.  The CLIST allocates the SDF PDS to both `OUTPUT5`
and `HALSDF`, matching `SDFPROCE.xpl`'s split: stand-alone uses `HALSDF`, while
in-chain sets `MISC | 4` for the "alternate DD name list" and uses `OUTPUT5`.
`ALL` mode additionally wants an OS/360 PDS directory block on device 3 —
`--pdsi=3` does not attach `INPUT(3)` — which has to be synthesised: a halfword
byte count, then per entry an 8-byte EBCDIC name, 3-byte TTR and a flags byte
whose low 5 bits give the count of user halfwords, so an entry occupies
`12 + 2*(flags & 0x1F)` bytes.

## DATABUF, and SDFPKG's statistics

PASS4 and `HALSTAT.xpl` both read SDFPKG's internal statistics out of a
structure they call DATABUF, and both find it the same way: call mode 0, then
take the base from `COMMTABL_FULLWORD(7)` — the `ADDR` field — and overlay
`DATABUF_BYTE`, `DATABUF_HALFWORD` and `DATABUF_FULLWORD` on it.

`sdfpkgInitialize` never wrote `ADDR`, so the base came out as 0 and every
statistic was read from low memory.  SDFLIST's "NUMBER OF SDFPKG LOCATES"
printed 150994948 = 0x09000004, which is `COREWORD(0)`, the `MONITOR(23)`
identifier descriptor; its "GETMAINS" printed 1062, which is the halfword at 36,
part of `MONITOR(13)`'s `NPVALS` pointer.  Not a byte-ordering problem — an
unimplemented feature.

Mode 0 now lays a 96-byte DATABUF at the base of the topmost memory region and
publishes its address in `ADDR`.  It cannot go in the caller's FCB area,
plausible though that would be, because HALSTAT calls mode 0 with a Paging Area
and no FCB area at all.  Field offsets are HALSTAT's, at `HALSTAT.xpl:661-687`,
which is the fullest map available.  Counters hook the natural places:
`reply()` for locates, the `fread` in the pager for reads, `selectSdf()` for
selects, `applyDisposition` for reserves.  `databufSync()` runs on every service
call rather than only at termination, because SDFLIST reads the statistics at
its `STATISTICS:` label *before* asking SDFPKG to terminate.  `VERSION` is set
at select time from the selected SDF's Phase 3 version, since HALSTAT gates
structure decisions on `IF VERSION >= 25`.

The six statistics SDFLIST prints are now sane, and three are independently
checkable: FCB area 2048 bytes and paging area 5 pages are exactly what
`INITIALI.xpl` passes, and 6 reads matches the SDF's "# OF LAST PAGE: 6".
GETMAINS is honestly 0 — nothing here does a GETMAIN.

## Corpus results

With SDF import in both compilers and the fixes above: **907 attempts, 843
successful, 59 not part of PASS, 0 cross-comparison differences and 0 SPACE
MANAGEMENT errors** — against 30 SPACELIB failures in the pre-fix baseline.  ZO3
skips fell from 90 to 34 and XI3 from 12 to 11.  PASS1-error skips rose from 1
to 17, which is the CS2 family now reporting its real DQ7 duplicate-name errors
instead of dying on the spurious BI002.

CS2IX4 is representative of that family and its residual failure is genuine:
DQ7 on `CSAS_PDT_PAR_ENTRY` and others, a real duplicate-name collision between
the CSAPDT and CS2PDT compools, on which both compilers agree exactly.

One Python defect surfaced once the BI002 line stopped masking it.
`HALINCL/DOWNSUM.py` used `len(h.DOWN_INFO)` where the XPL has
`RECORD_TOP(DOWN_INFO)`, which `SPACELIB.py` defines as `len - 1`.  `DOWN_INFO`
carries an unused element 0 — PASS1's `INITIALIZATION` does one `NEXT_ELEMENT`
before any downgrade is recorded — so a compilation with no `D DOWNGRADE`
directive at all printed an empty "DOWNGRADE SUMMARY" heading that the C rightly
did not.  Three sites corrected; sibling `CERRORS.py:73` already had it right.

## What is left

- SPACELIB's other abends — BI003, BI004 and BI010 — have never been seen in
  practice.  `compilePASS`'s space-management check is retained for them.
- The Python port's `SPACELIB.py` wants deletion rather than repair.  It does no
  space management: `RECORD_CONSTANT` appends Python objects to a list,
  `RECORD_ALLOC` returns `len()`, `RECORD_USED` is already a no-op.  Only the
  `VMEMREC` allocation is load-bearing, `VMEM3` taking `VMEM_PAD_ADDR[I]` from
  it, and whoever removes the rest should keep that in mind.
- `yaShuttle/ported/PASS1.PROCS/HALINCL/` is an untracked copy of
  `yaShuttle/ported/HALINCL/`, and it is the one on the PATH that `HAL_S_FC.py`
  actually imports.  No Makefile or script syncs them, so an edit to the tracked
  master alone changes nothing at runtime.
- `pass4 = False` in HALSFC: PASS4 works standalone but is not yet in the chain.
