THESE ARE CONTINUATION MARKERS, AND OI301700 HAS LOST THE CARDS THEY POINT AT.

An earlier version of this file argued they were revision flags -- 350 of the
382 do not reach column 71, 378 are complete statements, and none is followed
by anything resembling a continuation.  All true, all beside the point.

The OI340600 "as received" directory holds genuine CARD DECKS rather than
listings, and settles it: 688 cards there carry a non-blank column 72 and 688
of them are followed by a continuation card.  No exceptions, for any marker --
X, *, +, D and C alike.  OI340600's PREPARED sources keep all 688.  OI301700's
prepared sources keep 18 of 382.

So the extraction of OI301700 DROPPED 364 CONTINUATION CARDS, and the markers
below point at cards that are no longer there.  That is why they look like
flags and why FPMREL line 93 glues a comment onto a `ZH`.

Most of the lost cards carried only the tail of a COMMENT -- `HAS PASSED`,
`AND WAIT` -- so the object code does not depend on them, but ASM101S still
joins the following card and wrecks the statement.  Two ways forward: blank
column 72 wherever the continuation is missing, which assembles correctly
without inventing text; or restore the cards from OI340600's decks, which is
more faithful but crosses versions.  Neither has been done.

THE FOUR EXCEPTIONS WERE REAL TRUNCATION, AND ARE NOW RECOVERED (PFS commit
ec601001).  They are not macro parameters -- they are DC statements whose
bit-field operand overruns column 71 and lost its tail.  Each was restored as
a proper continuation card, resuming at column 16:

    FCMINSSL 1073   AL.15(FCMMZE  ->  AL.15(FCMMZERO)     certain
    FCMINSSL 1075   AL.15(FCMMZE  ->  AL.15(FCMMZERO)     certain
    FCMINSSL 1077   AL.15(FCMMZE  ->  AL.15(FCMMZERO)     certain
    FIOMGDSP 1041   AL.4(FIOM     ->  AL.4(FIOMWBLC)      inferred

The three FCMINSSL ones are certain: FCMMZERO is the only symbol in the corpus
beginning FCMMZE, and the arithmetic agrees with the listing's own assembled
words -- AL.8(FCMMSYNC=0), AL.5(FCMMIUA=B'01011'), AL.4 of the op-code,
AL.15(0) gives 00580000, 005C8000 and 00598000 at 0031A, 0031C and 0031E.

FIOMGDSP is an inference.  The candidates are FIOMWBLC, FIOMPOSC and FIOMZERO,
all three of them zero, so the assembled word is 005C0000 whichever it is and
no object code can tell them apart.  FIOMWBLC was chosen because it is the only
op-code symbol in that module used NOWHERE, while FIOMEWTC, FIOMPOSC and
FIOMWRTC each appear in exactly one command word, and because "WRITE BLOCK
COUNT" belongs in a write command word.  If better evidence turns up, that is
the one card to revisit.

Neither is verifiable by assembling yet: ASM101S reports "A bit length modifier
that is not a whole number of bytes (L.5) is not implemented", so these cards
generate no object code whatever text they carry.

ALREADY TRIED, so nobody tries it twice: restricting continuation to 'X' alone
and re-assembling these 73 files gives 7 byte-exact matches, exactly as many as
ASM101S's present rule of accepting any non-blank.  Whatever these markers mean,
they are not what is holding the corpus back.
