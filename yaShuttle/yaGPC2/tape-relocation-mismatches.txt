REFERENCE USED

NOT G9.fcm directly.  DASS_G9.ASC carries a change table listing every halfword
altered after the build, as address / symbol+offset / OLD value / NEW value:

     004D20    #PCGCCOM+007A    C1F1    C1A0
     004D21    #PCGCCOM+007B    70A2    0000

2396 such halfwords in G9; the dump holds the NEW value in all 2396.  Reverting
them reconstructs the as-built image, and THAT is what the tape is compared
against here.  Doing so is what makes the ground truth line up: phase 3's
boot-table blocks, which the machine demonstrably boots from, go

     blk 8   55.08%% -> 99.14%%        blk 3   99.70%% -> 100.00%%

tape writes 0000/c6c6 where the dump has c9fb.  Uncredited, correct blocks look
wrong -- #PCVTTCS scores 8.17%% raw, 98.88%% credited.)

WHAT IS LEFT, AND WHY IT IS A PUZZLE

After that, a residue remains with a very specific property:

    dump_value - tape_value  ==  (base address of some CSECT/DSECT) & 0xffff

usually the CSECT CONTAINING the halfword.  Worked example from $0VAASEQ
(starts 0x2bb9e); DASS_G9.ASC line 115985 identifies the halfword:

    02BBE2-02BBE3  $0VAASEQ+0044  C7F3  BD1F  02BD1F   BC 7,X'BD1F'  B ST#3008

The second halfword of a Branch-on-Condition is the branch TARGET.  The dump
holds BD1F (resolved, = 0x2bd1f); the tape holds 0181, and
0x2bd1f - 0x2bb9e = 0x181.  The tape has the SECTION-RELATIVE OFFSET where the
dump has the RESOLVED ADDRESS.

RULED OUT

   crediting the '*'-marked halfwords does not touch the OWN rows at all.
   $0VAASEQ scores 99.73%% against G9.fcm and 99.73%% against as-built --
   unchanged, so its residue is not a post-build upload.
2. Don's ~/Desktop/IPL/IPL.fcm.  The 8960-halfword $0VAASEQ block scores 0.23%%
   against IPL.fcm and 97.28%% against G9.fcm.  Not the source.

   OI340700 -- see PFS/OI340700/README.md) but it produces UNRELATED values, not
   a constant per-section offset.
