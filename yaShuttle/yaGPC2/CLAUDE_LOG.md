### [2026-07-29] Target: problems.md — automatic page-turn-on-overflow, a real yaGPC2 gap the whole project had been trusting the absence of
- **The user directly flagged a specific behavior of this session's own prior work that `yaHALMAT2` had been "too trusting" of**: `yaGPC2`'s `hal_newline()` (`src/halucp.c`) only ever turns a page via *explicit* `LINE`/`PAGE` pseudo-functions — it has **no automatic page-turn when a `PAGED` device's line count simply overflows** `linesPerPage` from ordinary `WRITE` advances alone. `yaHALMAT2`'s own `interp.c` had this exact behavior implemented correctly (`dm_advance_lines`, emitting a form-feed on overflow) — then **removed it earlier the same day**, reasoning from reading `yaGPC2`'s own (incomplete) `halucp.c` that its absence there meant real hardware doesn't do this. That inference was the actual problem: `yaGPC2`'s missing feature was treated as authoritative evidence about real hardware, when it was just an oversight.
- **Confirmed via the actual language spec** (`USA003087.txt` Sec. 12.4 rule 2): an explicit `SKIP(alpha)` may cross page boundaries ("SKIPs over page boundaries are allowed"), with no documented reason the *default* one-line advance (functionally an implicit `SKIP(1)`) would behave any differently — same "device mechanism," different trigger. The manual never spells out "and once the line count overflows, turn the page" explicitly because that's just how a physical line printer behaves, obvious enough not to need stating — unlike the deliberately-documented `SKIP`/`LINE`/`PAGE` pseudo-functions themselves, per the user's own explanation for why the docs are silent on this specific point.
- **Fixed in `yaGPC2`**: `hal_newline()` now checks, after incrementing the line counter, whether the channel is `PAGED` and the new count exceeds `linesPerPage` — if so, emits a bare form-feed (`0x0C`) and resets to line 1. Single choke point (every ordinary advance — implicit default, `SKIP(n)`, and `LINE`/`PAGE`'s own delta loops — already funnels through this one function), so it uniformly covers all cases and naturally reproduces `PAGE(beta)`'s own "relative line number unchanged" requirement (Fig. 12-7) as a side effect of always wrapping at exactly `linesPerPage` regardless of starting line. Also corrected `linesPerPage`'s own default from an unexplained `60` to `66` (the IBM 1403 line printer's documented lines-per-page, matching `yaHALMAT2`'s independently-researched same default).
- **Verified precisely against `yaHALMAT2`'s own new regression fixture spec** (`test_page_overflow_no_autoformfeed.hal`: 70 sequential `WRITE(6) I;`, no `LINE`/`PAGE`/`SKIP` anywhere) via a from-scratch equivalent compile: the form-feed lands exactly once, immediately after line 66's own newline and directly before line 67's own output — byte-for-byte matching. Re-ran the full corpus sweep: no new discrepancies introduced; `DEMO.hal`'s own original trigger (`WRITE(PRINTER) MY_STRUCTURE;`) now matches `yaHALMAT2` exactly at the form-feed position (only the already-accepted, non-comparable `D` out-of-bounds-read value remains as an unrelated diff).
