### [2026-07-29] Target: problems.md — automatic page-turn-on-overflow, a real yaGPC2 gap the whole project had been trusting the absence of
- **The user directly flagged a specific behavior of this session's own prior work that `yaHALMAT2` had been "too trusting" of**: `yaGPC2`'s `hal_newline()` (`src/halucp.c`) only ever turns a page via *explicit* `LINE`/`PAGE` pseudo-functions — it has **no automatic page-turn when a `PAGED` device's line count simply overflows** `linesPerPage` from ordinary `WRITE` advances alone. `yaHALMAT2`'s own `interp.c` had this exact behavior implemented correctly (`dm_advance_lines`, emitting a form-feed on overflow) — then **removed it earlier the same day**, reasoning from reading `yaGPC2`'s own (incomplete) `halucp.c` that its absence there meant real hardware doesn't do this. That inference was the actual problem: `yaGPC2`'s missing feature was treated as authoritative evidence about real hardware, when it was just an oversight.
- **Confirmed via the actual language spec** (`USA003087.txt` Sec. 12.4 rule 2): an explicit `SKIP(alpha)` may cross page boundaries ("SKIPs over page boundaries are allowed"), with no documented reason the *default* one-line advance (functionally an implicit `SKIP(1)`) would behave any differently — same "device mechanism," different trigger. The manual never spells out "and once the line count overflows, turn the page" explicitly because that's just how a physical line printer behaves, obvious enough not to need stating — unlike the deliberately-documented `SKIP`/`LINE`/`PAGE` pseudo-functions themselves, per the user's own explanation for why the docs are silent on this specific point.
- **Fixed in `yaGPC2`**: `hal_newline()` now checks, after incrementing the line counter, whether the channel is `PAGED` and the new count exceeds `linesPerPage` — if so, emits a bare form-feed (`0x0C`) and resets to line 1. Single choke point (every ordinary advance — implicit default, `SKIP(n)`, and `LINE`/`PAGE`'s own delta loops — already funnels through this one function), so it uniformly covers all cases and naturally reproduces `PAGE(beta)`'s own "relative line number unchanged" requirement (Fig. 12-7) as a side effect of always wrapping at exactly `linesPerPage` regardless of starting line. Also corrected `linesPerPage`'s own default from an unexplained `60` to `66` (the IBM 1403 line printer's documented lines-per-page, matching `yaHALMAT2`'s independently-researched same default).
- **Verified precisely against `yaHALMAT2`'s own new regression fixture spec** (`test_page_overflow_no_autoformfeed.hal`: 70 sequential `WRITE(6) I;`, no `LINE`/`PAGE`/`SKIP` anywhere) via a from-scratch equivalent compile: the form-feed lands exactly once, immediately after line 66's own newline and directly before line 67's own output — byte-for-byte matching. Re-ran the full corpus sweep: no new discrepancies introduced; `DEMO.hal`'s own original trigger (`WRITE(PRINTER) MY_STRUCTURE;`) now matches `yaHALMAT2` exactly at the form-feed position (only the already-accepted, non-comparable `D` out-of-bounds-read value remains as an unrelated diff). Full unit test suite re-run clean (same one pre-existing, unrelated `CVFX` fixture failure). Database (`demo_recursive_structure_write_spurious_form_feed`) updated to `fixed`/`yagpc2`.
- **All three previously-open issues are now resolved** (`multi_item_write_drops_nested_structure_vector_field` and `empty_character_write_padded_to_declared_length` independently fixed by `yaHALMAT2`'s own session; this page-turn issue fixed here) — database back to zero `open` issues.

### [2026-07-29] Target: problems.md — attempted `&ASM101S`-conditional MM14SN.asm fix (id 53), disproven and reverted; new lead found
- **At the user's direction, attempted the same `&ASM101S`-conditional-assembly technique already established for `CINDEX.asm`** on `RUNASM/MM14SN.asm`'s register-pair fragility (`datatypes_repeated_singular_inverse_unstable_result`, id 53, previously `not_a_bug`): two `SER F1,F1` insertions (after `ALOOP`'s `SER F0,F0`, and after `CTSW`'s single-precision pivot-candidate load) to stop the singularity check (`LER F0,F0`/`BE AOUT`) from reading leftover garbage in F0's uncleared companion register F1. Root-caused as a genuine, mechanical omission relative to the file's own established convention (`SER F3,F3` before F2's own `DER` use, a few lines below) — not speculative.
- **The fix itself checked out at the assembler level**: assembled cleanly; historical/non-ASM101S path confirmed byte-for-byte identical to `RUNLST/MM14SN.txt` (via a patched scratch copy of `ASM101S.py` with `&ASM101S` forced false); full `regressionASM101S.sh` corpus run showed no new divergences beyond the expected CINDEX/MM14SN pair. - **Discovered along the way**: the `nsts-sdl-dps` build pipeline's own embedded `asm101` package (used by its `make runtime` target) predates the `&ASM101S` convention entirely and has no reference to it at all — it silently produces the historical/unfixed object code regardless of source changes. This is a separate, pre-existing gap that would affect `CINDEX.asm`'s own already-accepted fix the same way; not yet reported or fixed, flagged here for later.

This disproves F1 leftover garbage as the (sole) cause of this specific instability.
- **New lead identified**: traced the pivot-search (`CTSW`) hit pattern across the three calls and found it genuinely differs at K=3/K=4 (different number of pivot-candidate updates per call), and the matrix-pointer register (R4→R1 at entry) is identical between the 1st/2nd calls but different for the 3rd — despite all three referencing the same HAL/S variable `A4A`. Suggests `A4A` may be mutated in place by `INVERSE`'s own Gauss-Jordan reduction, or a per-call-site compiler temporary isn't always freshly copied — a materially different, deeper bug than register-pair fragility, likely in HALSFC's or yaGPC2's HAL/S-to-AP101S calling convention rather than in `MM14SN.asm` itself.
- **Reverted the `MM14SN.asm` change** (harmless in isolation, but doesn't address the actual symptom, so not worth carrying unverified) and the matching copy pushed into the `nsts-sdl-dps` submodule checkout. Database entry reopened to `open`/`yagpc2`, with the disproof and new lead recorded in `detail` so this doesn't need re-deriving.
