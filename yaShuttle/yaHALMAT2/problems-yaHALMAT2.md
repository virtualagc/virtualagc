# yaHALMAT2 Problems Found During yaGPC2 Development

This file was generated by a Claude Code session working in `yaShuttle/yaGPC2/`
while investigating discrepancies between `yaGPC2` (a from-scratch AP-101S CPU
emulator) and `yaHALMAT2` (a HALMAT bytecode interpreter) for the same compiled
HAL/S programs. The investigation's scope was limited to WRITE/FILE output
parity between the two tools. Each item below was root-caused against a
**primary source** — either the real HALSFC/lnk101 compiler+linker toolchain
(producing real AP-101S machine code that yaGPC2 just executes), the HAL/S
Programmer's Guide (`yaHALMAT2/source-documentation/USA003087.txt`), or the
publicly-available Shuttle flight-software runtime library source
(`Source Code/PASS.REL32V0/RUNASM/*.asm`) — not just by comparing the two
tools' output and guessing which one is "wrong."

In every case below, yaGPC2's output was confirmed to match the real compiler
toolchain's actual behavior, so no yaGPC2 change was made; these are reported
here as candidate yaHALMAT2 bugs for someone working in this repo to evaluate
and fix.

## How to reproduce / cross-check any of these

All of these were investigated by compiling a small `.hal` test program with
the real HAL/S compiler and AP-101S linker, then running it in **both**
`yaGPC2` and `yaHALMAT2` with matched output-width settings, and separately
reading the compiled AP-101S assembly listing to see exactly what machine code
the real compiler generated for the construct in question.

```sh
export PATH="/home/rburkey/git/virtualagc/yaShuttle/Source Code/PASS.REL32V0:/home/rburkey/donschmidt/nsts-sdl-dps/build/bin:$PATH"
cd <some-scratch-dir>          # HALSFC changes cwd as a side effect; use absolute paths after this
cp <path-to-test>.hal .
HALSFC <test>.hal -o <test>.obj \
  --parms="LIST,NOTABLES,SRN,TEMPLATE,NOLFXI,REGOPT,VARSYM,CARDTYPE=PFS.STANDALONE" \
  --force --clean
# current.results/pass2.rpt is the compiled AP-101S assembly listing -- read
# this to see exactly what real machine code was generated.
lnk101 current.results/<test>.obj -o <test>.fcm --json-symbols <test>-lnk101.json
```

Then run the same `.fcm`/HALMAT through both tools with **matched line-width
settings** (yaHALMAT2 defaults to 132 columns, yaGPC2/gpc default to 240 —
a mismatch here produces spurious diffs unrelated to any real bug, as
happened at least once during this investigation — see item 3 below).

Test sources referenced below all live in `src/tests/hal/` in this repo.

## 1. BIT-to-INTEGER conversion zero-extends instead of sign-extends (OPEN)

**Severity: real bug, not yet fixed.**

When converting a `BIT` value to `INTEGER`, yaHALMAT2 zero-extends the bit
pattern. The HAL/S Programmer's Guide (`source-documentation/USA003087.txt`,
Appendix A, "STANDARD CONVERSION FORMATS" / "CONVERSIONS TO INTEGER TYPE")
explicitly specifies that a bit type converts to integer "by regarding it as
the bit pattern of a **signed** integer of the desired precision" — i.e. this
should be a sign-extending reinterpretation, not a zero-extending one.

`gpc`/`yaGPC2`'s sign-extending behavior was confirmed spec-correct against
this exact wording. yaHALMAT2's zero-extension is the bug.

**Affected test programs** (all in `src/tests/hal/`):
- `test_bit.hal`
- `test_bit_at_partition.hal`
- `test_subbit_assign.hal`
- `test_init8.hal`

**Suggested fix**: find yaHALMAT2's BIT→INTEGER conversion code path and
change it to sign-extend from the bit pattern's high-order bit (of the
declared/converted bit width), not zero-extend.

## 2. SCALAR-to-INTEGER exact-.5 rounding ties round the wrong way (OPEN)

**Severity: real bug, not yet fixed.**

When a `SCALAR` value that is exactly `N.5` is converted to `INTEGER`,
yaHALMAT2 rounds away from zero (e.g. 2.5 -> 3). The real AP-101S/HAL-S
runtime does not do this.

Root cause, confirmed by compiling `test_stoi.hal` and reading the generated
AP-101S assembly (`current.results/pass2.rpt`): the compiler emits a call to
the linked-in runtime-library routine `ETOH` (source at
`Source Code/PASS.REL32V0/RUNASM/ETOH.asm`, public-domain Shuttle
flight-software runtime library). `ETOH`'s actual algorithm is: `CVFX`
(truncating float-to-fixed conversion) followed by a hand-coded rounding-bias
sequence:
```
A   R5,=X'7FFF'
    (conditional) A R5,=X'1'
NHI R5,X'FFFF'
```
This is real 1980s flight-software rounding logic — a truncate-then-bias
scheme that, for exact `.5` values, ends up rounding toward zero, not away
from it. `gpc`/`yaGPC2`'s "round toward zero at exact .5" is simply the
faithful result of executing this real algorithm (yaGPC2 doesn't reimplement
SCALAR→INTEGER conversion itself — it runs the real compiled AP-101S machine
code for `ETOH` through its CPU emulator, which is already validated against
~700K instruction-level fixtures). yaHALMAT2's "round away from zero" is the
divergent behavior.

**Affected test program**: `test_stoi.hal`

**Suggested fix**: read `ETOH.asm` directly (it's short) and either port its
exact truncate-then-bias algorithm, or at minimum match its rounding
direction for the exact-.5 case (round-half-toward-zero, i.e. more precisely:
truncate, then add a bias of `0x7FFF` before an arithmetic shift/mask — see
the source for the precise bit-level behavior across positive/negative
values, since a naive "round half down" is not obviously equivalent for
negative inputs and should be checked against `ETOH.asm`'s actual code path,
not just the exact-.5 positive case this test happens to exercise).

## 3. Bit-radix literal width defaulted to a flat 32 bits — FIXED per user, 2026-07-27

**Severity: was a real bug; user has since reported this is fixed on the
yaHALMAT2 side. Included here for the record / in case verification is
useful.**

`HEX'...'`/`BIN'...'`/etc. bit-radix literals (e.g. `WRITE(6) HEX'1234';`)
were defaulting to a flat 32-bit width in yaHALMAT2 (a deliberate design
choice made under uncertainty when the correct rule couldn't be determined
from the manuals alone, per the user).

The correct rule, empirically confirmed by compiling 15 `WRITE(6)
<radix-literal>;` variations through the real HALSFC compiler and reading
each one's compiled `LHI R6,<N>` width-immediate operand directly:

> **width = (bits-per-digit for that radix) × (number of digit characters
> written in the source), with leading zeros counting toward the digit
> count** (not stripped before computing width).

Confirmed for:
- **HEX** (4 bits/digit): 1 through 8 digits tested, including
  `HEX'00045'` (2 leading zeros, 5 digits total) → 20 bits; `HEX'0'` → 4
  bits; `HEX'00'` → 8 bits.
- **BIN** (1 bit/digit): `BIN'00111'` → 5 bits; `BIN'1'` → 1 bit;
  `BIN'0000000000000001'` → 16 bits; `BIN'101'` → 3 bits.

This is baked directly into the compiled AP-101S machine code by the real
compiler (an `LHI R6,<width>` immediately preceding the `#QBOUT` runtime
call) — it is a compile-time-computed constant, not a runtime default.

**Affected test program**: `test_bit_write.hal`

**If re-verifying this fix**: check both HEX and BIN (and ideally OCT/DEC if
yaHALMAT2 supports those radix literals) against the digits×bits-per-digit
rule above, including leading-zero cases, not just a single spot check.

## 4. test_tint_null_terminal — likely the SAME bug as #3, worth re-checking now that #3 is fixed

**Severity: unclear — HIGH CONFIDENCE it's the same root cause as item 3
above, but NOT fully empirically confirmed** (this specific test failed to
compile standalone with the `--parms` used throughout this investigation —
`ILLEGAL CARD TYPE` at its `STRUCTURE` declaration, likely needing a
different `CARDTYPE`/column-format setting given its unusual leading comment
block and a `Y %SVCI(0);` line; this was a compiler-invocation/tooling
mismatch, not investigated further).

The test declares `STATUS BIT(16)` explicitly as a structure field, so
`WRITE(6) FWDSENSORS.STATUS;` should output using the **declared field's
width** (16 bits, i.e. "4 groups of 4" hex nibbles, matching `gpc`/yaGPC2's
observed output). yaHALMAT2 was observed outputting "8 groups of 4" (32
bits) — consistent with the same flat-32-bit-default bug as item 3, just
triggered by a declared-width BIT field's initializer rather than a bare
literal in a WRITE statement.

**Suggested next step**: now that item 3 is reportedly fixed, re-run this
test (fixing the `CARDTYPE`/compile-parms issue first — try without
`CARDTYPE=PFS.STANDALONE`, or inspect the test's own header comment for
compiler-directive hints) and check whether it now produces 16-bit ("4
groups of 4") output automatically. If it doesn't, the bug is somewhere
distinct from item 3 — likely in how a *declared* bit-field's width is
threaded through to WRITE, as opposed to a bare radix literal's width.

**Affected test program**: `test_tint_null_terminal.hal`

## 5. CHARACTER(BIT) simple-form conversion applies radix-style decimal conversion instead of bit→character mapping (OPEN)

**Severity: real bug, not yet fixed.**

`test_bit_conv.hal` does `C1 = CHARACTER(B1);` where `B1` is a 4-bit string
`0101` — this is the **simple form** of the `CHARACTER()` conversion (no
`@DEC`/`@OCT`/`@HEX` radix qualifier). Per USA003087 Sec. 21.4's own worked
example, the simple form of bit-to-character conversion produces a character
string where "the number of characters is the same as the number of bits" —
i.e. each bit becomes a literal `'0'` or `'1'` character in the output
string. For a 4-bit `0101` input, this correctly gives a 4-character string
(`gpc`/yaGPC2 produces `"00001100"` for the test's actual multi-field output,
confirmed against this exact worked example).

yaHALMAT2 outputs `"12"` for the same conversion — this looks like it is
incorrectly applying **radix-style decimal conversion** (as if a `@DEC`
qualifier were present) to a plain simple-form `CHARACTER()` call.

**Affected test program**: `test_bit_conv.hal`

**Suggested fix**: find yaHALMAT2's `CHARACTER()` conversion dispatch and
confirm it only applies radix/decimal interpretation when an explicit `@DEC`/
`@OCT`/`@HEX` qualifier is present in the source; the no-qualifier
("simple form") path should map each bit to a `'0'`/`'1'` character
1:1, not interpret the bit pattern as a number.

## 6. test_subbit_scalar — genuinely ambiguous, not a clear-cut bug (LOW PRIORITY / informational)

**Severity: unclear whether this is a bug at all** — flagging for awareness,
not as a confirmed defect.

`B2 = SUBBIT(S1);` (S1 a single-precision SCALAR) correctly copies S1's full
32-bit IBM-hex bit pattern into B2 in both tools (confirmed: this matches
USA003087 Sec. 21.5's SUBBIT reference-context rule, N=32 for
single-precision SCALAR). The divergence is in the *subsequent*
`WRITE(6) INTEGER(B2);`:

- The real compiler generates `SLL R7,16` before treating the result as a
  16-bit halfword (via `#QHOUT`) — i.e. it takes B2's **lower** 16 bits
  (which are `0x0000` for `S1=2.5`, i.e. IBM-hex `0x41280000`), hence
  `gpc`/yaGPC2 output "0".
- yaHALMAT2 outputs `1093140480` (= `0x41280000` exactly, decimal), i.e.
  B2's full untruncated 32-bit pattern — meaning it inferred a
  double-precision (32-bit) result for this bare `INTEGER(bit-expression)`
  call instead of single-precision (16-bit).

Neither the HAL/S Programmer's Guide nor (as far as this investigation went)
the Language Specification pins down what precision a bare `INTEGER(exp)`
should default to for an arbitrary bit expression — only SUBBIT's own
N-bits-visible rule is specified precisely, and that part both tools already
agree on. This is genuinely unresolved which behavior is "more correct" in
general; it's included here only because it's a real, reproducible
divergence, not because there's a confirmed spec violation on yaHALMAT2's
side.

**Affected test program**: `test_subbit_scalar.hal`

**Suggested next step if pursued**: compile a few more `INTEGER(<bit
expression>)` variants with declared vs. inferred precisions through the
real compiler to see if there's a consistent rule (e.g. "bare INTEGER()
without an explicit precision always defaults to single/16-bit unless the
source bit-string's own declared length forces double") before changing
anything, since this one is not backed by an explicit manual citation the
way items 1-5 are.
