### [2026-07-30] Target: state.h / interp.c (timing model)
- yaGPC2 gained a `halmat on` debug-prompt command tagging each HAL/S statement's AP-101S instructions with their owning HALMAT word indices (`H=55,57,...`), enabling real per-statement/per-RTL-call timing instead of the flat per-HALMAT-instruction tick model.
- Wrote a call-stack-aware parser (`/tmp/.../scratchpad/rtl_trace/parse_rtl.py`, scratch-only, not in repo) that reconstructs true call nesting from the AP-101S opcodes themselves (SCAL/BAL push, SRET/SVC/register-target-branch pop) so nested RTL calls (e.g. COUTP internally calling CASV) are folded into the one outermost call actually made by compiled program code, not double-counted.
- Ran it across ~185 `tests/hal/*.hal` fixtures via `compileLinkRun --debug` + `halmat on`/`htrace on`/`continue`. Zero unclassified push/pop transitions across the whole sample after two small fixes (SVC as a pop on HAL/S SEND ERROR unwinds; tolerating a rare line where an interleaved SEND ERROR message eats the `[nnn] T=...` prefix).
- Findings: RTL/library-call time is 0%-99.4% of total program time across fixtures (median 55.8%). `IOINIT` (n=1055, CV=0.27) and `COUTP` (n=186, CV=0.14) are well-characterized and fairly flat; matrix/vector RTL routines (`MMWSNP`, `MM14SN`, `MM12SN`, `RANDOM`) show CV up to 2.44 -- clearly size/data-dependent, not modelable as a flat average. (Correction to this bullet's original wording: I'd said HELLO's `WRITE(PRINTER)` statement -- ~209.6us/execution real, IOINIT+COUTP+IOINIT+CATV -- was a "~700x undercount" against "~297ns currently modeled." That's a unit error: 1 tick at the *old* 16800-ticks/sec rate is 1e6/16800 ~= 59.52 MICROseconds, not nanoseconds, so 5 non-zero-cost opcodes x 1 tick was actually ~297.6us modeled -- an OVER-count of ~42% for that specific statement, not a 700x undercount. The real picture, confirmed once Phase 1 below was implemented and validated: pure-compute opcodes were being substantially OVER-priced by the old flat 59.52us/tick charge (real local costs mostly run 0-30us), while I/O/RTL-heavy statements were UNDER-priced (RTL call costs of 20-200+us/call weren't modeled via any opcode at all) -- a mixed picture, not a uniform direction, which is exactly what the pre-existing per-fixture spread (HELLO under-corrected, scalar_arith over-corrected) already implied.)
- Not yet done: deciding+implementing the actual charging mechanism in `interp.c` (candidate: charge the measured cost at natural statement-boundary opcodes like `XXND`, informed by item count/type at that point, rather than per-individual-opcode) -- deliberately left uncommitted since it involves several open design choices (item-type cost breakdown, how to model the strongly size-dependent matrix/vector/random routines, whether math BFNC calls need the same treatment) that should get the user's input rather than being decided unilaterally overnight. No yaHALMAT2 source files were changed this session.
- Tried the complementary "local" (non-RTL, in-compiled-code) half of the model: per H=-statement-block, subtract measured RTL-call time from the block span and equal-divide the remainder across that statement's non-zero-cost opcodes (`parse_local.py`, same scratch dir). Result is noisy and not yet trustworthy: I/O-related opcodes (XXST, XXAR, CLOS) show huge variance (CV up to 4.9, one outlier of 2012us) that looks like leaked/unsubtracted RTL-call time rather than genuine local cost -- the block-boundary containment test (an RTL call counts as "inside" a statement only if its start/end both fall within that statement's instruction span) is evidently too naive near I/O statements and program exit. Needs more careful boundary handling before it's usable; the RTL-call side (previous bullets) remains solid and is not affected by this.
- Fixed the above. Rewrote `parse_local.py` to derive local time in a single instruction-by-instruction pass (same call-nesting tracking as `parse_rtl.py`) instead of subtracting call spans from H=-line-to-H=-line timestamps -- every microsecond in the trace now lands in exactly one of "local" or "call", self-checked per fixture via `local_total + call_total == (last root T - first root T)`. That check also caught a second, worse bug: the root/depth check was reading the call-depth counter *before* that instruction's own push/pop transition was applied, so the first instruction back at root after every single call return was misclassified as still inside the call, silently dropping one instruction's local time per return (171 of 184 fixtures were out of balance because of it, not just the handful of I/O-heavy ones originally suspected). After both the reordering fix and the rewrite, only 19 fixtures still fail the balance check, and all 19 turned out to be READ-statement fixtures run with no real stdin data behind them (traces end mid-call/mid-stall rather than completing) -- a capture-setup artifact, not an algorithm bug, so those are now excluded from the aggregate rather than chased further. Per-opcode local cost is now sane: XXAR (n=518, mean=19.7us, CV=0.57), XXST (n=345, mean=20.7us, CV=0.47), with the earlier multi-thousand-microsecond outliers gone.
- Implemented and committed Phase 1 of the integration plan: `interp.c`'s `op_is_zero_cost_time()` (bool) became `op_cost_ticks()` (int64_t), keyed on the full instruction so it can extend to `ins->tag` for BFNC later. Assignment/arithmetic/loop-control/call opcodes with clean RTL-free local measurements got real per-opcode weights (SASN=9, IASN=5, BASN=2, CASN=13, VASN=7, MASN=29, IADD=1, SADD=1, DFOR=0, EFOR=1, CTST=2, CLOS=4, RTRN=2, PCAL=5, FCAL=6, LFNC=3 ticks); everything else not yet measured (including XXST/XXAR and all I/O, deliberately deferred to a follow-on phase per the plan) keeps a flat 60-tick default, chosen to exactly reproduce the OLD flat charge's real duration so the unit change doesn't silently perturb unmeasured opcodes. `HALMAT_TICKS_PER_SECOND` moved from 16800 to 1000000 (1 tick == 1 microsecond exactly) now that weights are individually-measured microsecond values rather than one pooled multiplier -- confirmed no other hardcoded numeric dependency on the old rate exists (burst/signal pacing derive from the constant symbolically; two stale comments citing the old rate updated for accuracy).
- Full regression suite passes clean after rebuild, including every `sched_*`/`wait_*` fixture -- a real risk flagged before implementing (non-uniform per-opcode weights, unlike a uniform tick-rate rescale, can in principle reorder two racing/preempting tasks if their instruction mixes differ) did not manifest as any observable failure. `runtime` fixture's expected value updated a third time (small residual shift, same pattern as its two prior updates).
- Validated against the original 6-fixture real-yaGPC2-vs-yaHALMAT2 dynamic comparison: `int_arith2` is now nearly exact (ratio 0.996, real=671.98us vs modeled=675.00us); `scalar_arith`'s prior 3.2x over-correction shrank to 1.59x (real=130.60 vs modeled=208.00, was 416.67 before Phase 1); `bit`/`pcal`/`write_lit` now sit in the 0.57-0.71 ratio range (previously untracked precisely, but consistent with the same partial-improvement pattern). `HELLO` (I/O-dominated, 72.3% RTL time) got NUMERICALLY worse in isolation (ratio 1.22 -> 1.52, real=10970.23 vs modeled dropping from 8988.10 to 7225.00) -- expected, not a regression: Phase 1 correctly stopped over-pricing HELLO's cheap, frequently-repeated loop-control opcodes (DFOR/EFOR in its nested DO FOR), which happened to be accidentally compensating for the completely-unmodeled RTL call cost of its dominant WRITE statements. That accidental compensation is exactly what Phase 2 (I/O/RTL modeling, not yet started) needs to replace with the real thing.
