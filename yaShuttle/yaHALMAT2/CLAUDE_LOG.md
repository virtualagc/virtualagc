### [2026-07-24] Target: reengineered-documentation/class-6/IASN.md, class-5/SASN.md
- User-reported (GOOGLE-PARALLAX.hal): `DISTANCE`, a `SCALAR DOUBLE`, printed with single-precision `WRITE` formatting (7 fraction digits/14-char width) instead of double (16/23). Traced to two compounding bugs in `OP_IASN`/`OP_SASN` (`interp.c`), both around the destination's *true* declared type/precision never being consulted at assignment time:
  1. `IASN.md`'s own Unresolved Questions section already documented (from an earlier session) that PASS1 emits `IASN`, not `SASN`, for a genuinely `SCALAR` receiver whenever the literal being assigned is whole-valued (`EOR = 93000000.0;`) — noting "the generated machine code still stores the value as a float" — but this was only ever recorded as an open question, never actually corrected in the interpreter. `OP_IASN`'s handler unconditionally forced the resolved value to `RV_INTEGER` before the write, and `write_syt_entry`'s first-write type inference trusts that kind blindly — so a plain `SCALAR`/`SCALAR DOUBLE` destination hit this way got silently mistyped `SYT_TYPE_INTEGER` and lost its scalar-ness (and, for a `DOUBLE` receiver, its precision) for the rest of the program. Traced from `DISTANCE` back to `EOR = 93000000.0;` as the actual origin.
  2. Separately, even via ordinary `SASN` (a non-whole-valued literal, e.g. `ANGULAR_SHIFT = 0.5;`), the literal's own litfile-encoded precision (always single — `literal.c` has no per-context double form) was never widened to match a `DOUBLE`-declared receiver; assignment performed no automatic precision conversion at all, so a `SCALAR DOUBLE` variable assigned a plain literal stayed single-precision-tagged indefinitely. (Once a value *is* correctly tagged double, arithmetic itself already propagates precision correctly — `halmat_scalar_add`/etc.'s `dbl = a.double_precision || b.double_precision` — so this was purely an assignment-time gap, not an arithmetic one.)

  Both fixed together: `OP_IASN`/`OP_SASN` now looks up the destination's declared class/precision via the symbol table when it's a plain (`QUAL_SYT`) reference — the same established technique as `OP_TINT`'s identical per-field class correction and `bind_call_argument`'s parameter-precision conversion (`HALMAT_SYM_FLAG_SINGLE`/`_DOUBLE`, `scale_precision()`) — and lets it override the opcode's nominal class (fixing bug 1) and normalize the resolved value's precision to the declared one on *every* write, not just the first (fixing bug 2). Regression fixture: `src/tests/hal/test_scalar_double.hal` (mirrors `EOR`/`ANGULAR_SHIFT`/`DISTANCE` from the real program), wired into `run_all.sh`; confirmed to fail on pre-fix code reproducing the exact user-reported symptom (`EOR` printed as a bare integer, `ANGULAR_SHIFT`/`DISTANCE` single-precision-formatted), passes after, and confirmed against a real `GOOGLE-PARALLAX.hal` run (`DISTANCE` now prints with full double-precision formatting; the computed value itself also shifts slightly in its low digits versus the old single-precision-computed result, as expected once the whole chain is genuinely computed in double). `IASN.md`'s Unresolved Questions entry should be updated from "not fully explained at the bit level" to note it's now corrected at the interpreter level (symbol-table class override), and both files should gain a short note on the new per-write precision normalization to the destination's declared SINGLE/DOUBLE.
