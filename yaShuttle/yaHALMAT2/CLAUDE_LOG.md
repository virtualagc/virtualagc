### [2026-07-30] Target: state.h / interp.c (timing model)
- yaGPC2 gained a `halmat on` debug-prompt command tagging each HAL/S statement's AP-101S instructions with their owning HALMAT word indices (`H=55,57,...`), enabling real per-statement/per-RTL-call timing instead of the flat per-HALMAT-instruction tick model.
- Wrote a call-stack-aware parser (`/tmp/.../scratchpad/rtl_trace/parse_rtl.py`, scratch-only, not in repo) that reconstructs true call nesting from the AP-101S opcodes themselves (SCAL/BAL push, SRET/SVC/register-target-branch pop) so nested RTL calls (e.g. COUTP internally calling CASV) are folded into the one outermost call actually made by compiled program code, not double-counted.
- Ran it across ~185 `tests/hal/*.hal` fixtures via `compileLinkRun --debug` + `halmat on`/`htrace on`/`continue`. Zero unclassified push/pop transitions across the whole sample after two small fixes (SVC as a pop on HAL/S SEND ERROR unwinds; tolerating a rare line where an interleaved SEND ERROR message eats the `[nnn] T=...` prefix).
- Findings: RTL/library-call time is 0%-99.4% of total program time across fixtures (median 55.8%), confirming the current flat "1 tick per real HALMAT instruction" model drastically undercounts I/O- and math/library-heavy code -- concretely, HELLO.hal's repeated `WRITE(PRINTER)` statement measures ~209.6us/execution (IOINIT+COUTP+IOINIT+CATV) against ~297ns currently modeled for its 5 non-zero-cost opcodes, a ~700x undercount. `IOINIT` (n=1055, CV=0.27) and `COUTP` (n=186, CV=0.14) are well-characterized and fairly flat; matrix/vector RTL routines (`MMWSNP`, `MM14SN`, `MM12SN`, `RANDOM`) show CV up to 2.44 -- clearly size/data-dependent, not modelable as a flat average.
- Not yet done: deciding+implementing the actual charging mechanism in `interp.c` (candidate: charge the measured cost at natural statement-boundary opcodes like `XXND`, informed by item count/type at that point, rather than per-individual-opcode) -- deliberately left uncommitted since it involves several open design choices (item-type cost breakdown, how to model the strongly size-dependent matrix/vector/random routines, whether math BFNC calls need the same treatment) that should get the user's input rather than being decided unilaterally overnight. No yaHALMAT2 source files were changed this session.
- Tried the complementary "local" (non-RTL, in-compiled-code) half of the model: per H=-statement-block, subtract measured RTL-call time from the block span and equal-divide the remainder across that statement's non-zero-cost opcodes (`parse_local.py`, same scratch dir). Result is noisy and not yet trustworthy: I/O-related opcodes (XXST, XXAR, CLOS) show huge variance (CV up to 4.9, one outlier of 2012us) that looks like leaked/unsubtracted RTL-call time rather than genuine local cost -- the block-boundary containment test (an RTL call counts as "inside" a statement only if its start/end both fall within that statement's instruction span) is evidently too naive near I/O statements and program exit. Needs more careful boundary handling before it's usable; the RTL-call side (previous bullets) remains solid and is not affected by this.
- Fixed the above. Rewrote `parse_local.py` to derive local time in a single instruction-by-instruction pass (same call-nesting tracking as `parse_rtl.py`) instead of subtracting call spans from H=-line-to-H=-line timestamps -- every microsecond in the trace now lands in exactly one of "local" or "call", self-checked per fixture via `local_total + call_total == (last root T - first root T)`. That check also caught a second, worse bug: the root/depth check was reading the call-depth counter *before* that instruction's own push/pop transition was applied, so the first instruction back at root after every single call return was misclassified as still inside the call, silently dropping one instruction's local time per return (171 of 184 fixtures were out of balance because of it, not just the handful of I/O-heavy ones originally suspected). After both the reordering fix and the rewrite, only 19 fixtures still fail the balance check, and all 19 turned out to be READ-statement fixtures run with no real stdin data behind them (traces end mid-call/mid-stall rather than completing) -- a capture-setup artifact, not an algorithm bug, so those are now excluded from the aggregate rather than chased further. Per-opcode local cost is now sane: XXAR (n=518, mean=19.7us, CV=0.57), XXST (n=345, mean=20.7us, CV=0.47), with the earlier multi-thousand-microsecond outliers gone.
