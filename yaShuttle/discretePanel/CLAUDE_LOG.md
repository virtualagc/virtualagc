### [2026-11-17] Target: README.md, HANDOFF-meds2-py.md
- MEDS2.py on a Raspberry Pi 5 (any BCM2712 board: Pi 5, Pi 500, CM5) sets MESA_GL_VERSION_OVERRIDE=4.1 and MESA_GLSL_VERSION_OVERRIDE=410 itself, before PyQt6 is imported (_pi5_gl_override, matched on "brcm,bcm2712" in /proc/device-tree/compatible; values already in the environment win). The Pi 5's Mesa v3d driver offers desktop GL only up to 3.1 (no tessellation or fp64 in the GPU), so the 4.1 core request failed with EGL_BAD_MATCH and no MDU could draw. The renderer's shaders are GLSL 330 and nothing it uses is missing, so with the override it draws correctly (checked with --dev crt1). Software rendering (LIBGL_ALWAYS_SOFTWARE=1, llvmpipe, GL 4.6) is not an alternative there: the whole window came out sheared under Wayland, cache on or off.

### [2026-11-17] Target: README.md, PORTVIEW_PLAN.md
- portview.py reads GL_MAX_TEXTURE_SIZE once (max_texture_size) and halves any image larger than it before its first upload, with one line saying so ("... is larger than this GPU's largest texture (4096 px): uploading it at 1/2 size"), instead of failing with GL_INVALID_VALUE and retrying. SiteStream (a site's imagery streamed in during a run) drops the mip levels over the limit; before, an oversized ring there would have failed and the whole site been given up as Blue Marble only. The size failure used to turn off on-upload compression for every texture (TEXTURES['nocompress']), as its first retry; now compression stays on. Halving 8-bit images is done in 16-bit integers (half_image), the same pixels as before without a float32 copy (1.6 GB for a 16384 x 8192 Blue Marble). On the Pi 5, --test reached "truth data back" at 26 s instead of 35 s.

### [2026-11-17] Target: HANDOFF-meds2-py.md (§12 symptom table)
- Raspberry Pi 5: with NSTS_MEDS_CACHE on (the default), about half of an MDU's frames were black but for the header clock, which looked "garbled" (two seconds' values superimposed); the user saw it as every other screen lost. NOT the bus: the GPC's DK fills arrive complete (every transfer checked against its count; no "transfer abandoned"), and the 157-halfword fill at DYNAMIC 0x1a0e that alternates with the 230-halfword one at 0x1a06 replays into a fresh MDU and draws correctly. The black frames are the repaints that only copy the cached page (clock, flash edge), never a rebuild: Qt clears the QOpenGLWidget's framebuffer before every paintGL (NoPartialUpdate) and the tile-based v3d driver let the clear land after _renderCached's blit. The cached textures read back sound; resetting blend/depth before the blit and NSTS_MEDS_SAMPLES=0 did not help; NSTS_MEDS_CACHE=0 did (and used no more CPU). Fix: MDUGLWidget sets UpdateBehavior.PartialUpdate when _ON_PI5 (the BCM2712 check, now returned by _pi5_gl_override) and the cache is on; the cached path writes every pixel with its blit, so the clear is not needed. Measured on live traffic relayed into a second MDU: 54/100 frames black before, 0/120 after. Other platforms unchanged.

### [2026-11-18] Target: HANDOFF-meds2-py.md (§12 symptom table)
- Raspberry Pi 5, STS-134 rendezvous: PASS raised I/O ERROR CRT1/CRT2 every few minutes and once lost a whole keyboard entry (SPEC 3 4 PRO never reached PASS; run rendezvous-20261118-084825 stopped at the /034/ wait). Cause: Object3D.parent and parent.children made every scene node a reference cycle, and the pages rebuild their meshes constantly, so each MEDS2 left 150,000-580,000 cyclic objects (Mesh, BufferGeometry, BufferAttribute, Vec3, Euler, ...) for a generation-2 collection every 28-36 s. On the Pi a full collection took 320-520 ms with the GIL held. The IDP's BusPump thread could not answer a poll for that long, yaGPC2's peer hold gives up at 200 ms, the BCE6/BCE7 receive timed out, and the keyboard message pollResponse had already popped for that reply was gone. Measured with a faulthandler watchdog and gc.callbacks timing loaded through sitecustomize (no source change). Fix: Object3D.parent is a property over a weakref, so a discarded subtree is freed by reference counting. Same STRKEND repro, before -> after: full collections 320-520 ms -> 45-60 ms (one of 134 ms), freeing about 200,000 objects -> 0-2,400; over the whole flight to POSTTI (about 9,950 BCE6/BCE7 peer holds each run), holds of 100 ms or more 240 -> 0 (longest after: 50-100 ms, twice), mean hold 5.8 -> 1.9 ms, holds that expired with no reply 41 -> 0, CRT receive timeouts 40 -> 0, new I/O ERROR fault summaries 7 -> 0; SPEC 34 and the rest of the keyboard entries all went through. (The I/O ERROR CRT2 at 17:29:19 on every fault line comes from the STRKEND capture on the tape and appears in all runs.) x86 showed no errors because its collections fit inside the 200 ms hold.
- Follow-up, the full collections that were left (about 45 ms on the Pi, every 15-50 s): a garbage census found the rest of MEDS2's cyclic garbage hanging off five nested recursive helpers named walk (GLRenderer.render, VectorDisplay.flatten, Screen_AE_PFD._disposeGroup and two XML walkers). A nested function that calls itself is a cycle through its own cell, and it keeps what it closes over (a frame's mesh lists) until a full collection: about 36,000 objects per sample on CRT1. Each now ends with `del walk`. main() also calls gc.freeze() 20 s after start and gc.collect()+gc.freeze() every 60 s, so full collections skip the ~50,000 objects that live as long as the process (NSTS_MEDS_GC_FREEZE=0 turns it off; not Pi-specific). A freeze before the walk fix made things worse on CRT1 (a 184 ms collection), because the freeze made full collections frequent while the walk cycles still came in large batches. With both changes, same STRKEND -> POSTTI replay with portview, the GC-timing hook loaded: full collections median 9 ms, max 58 ms (from about 45/134 ms), finding no garbage; peer holds max 26 ms (yaGPC2's always-on counters), 0 expired. Master without either change and without the hook measured max 29 ms, so the hook itself costs some margin. That replay is 46 minutes long; the freeze still needs a run of several hours (launch to landing) to show that nothing builds up.
