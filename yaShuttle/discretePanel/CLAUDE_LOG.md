### [2026-11-17] Target: README.md, HANDOFF-meds2-py.md
- MEDS2.py on a Raspberry Pi 5 (any BCM2712 board: Pi 5, Pi 500, CM5) sets MESA_GL_VERSION_OVERRIDE=4.1 and MESA_GLSL_VERSION_OVERRIDE=410 itself, before PyQt6 is imported (_pi5_gl_override, matched on "brcm,bcm2712" in /proc/device-tree/compatible; values already in the environment win). The Pi 5's Mesa v3d driver offers desktop GL only up to 3.1 (no tessellation or fp64 in the GPU), so the 4.1 core request failed with EGL_BAD_MATCH and no MDU could draw. The renderer's shaders are GLSL 330 and nothing it uses is missing, so with the override it draws correctly (checked with --dev crt1). Software rendering (LIBGL_ALWAYS_SOFTWARE=1, llvmpipe, GL 4.6) is not an alternative there: the whole window came out sheared under Wayland, cache on or off.

### [2026-11-17] Target: README.md
- portview.py does the same on a Pi 5 (BCM2712), in its Linux setup before OpenGL and Qt load. Checked with --test: the 4.1 core context is made and the forward view draws (stars and sky). The Pi 5's largest texture is 4096 px, so every 8192 and 16384 px texture fails its first upload (GL_INVALID_VALUE) and is uploaded at 1/2 size (Blue Marble at 1/4) by the existing fallback; slow (about 17 s of retries) but it works.

### [2026-11-17] Target: README.md, PORTVIEW_PLAN.md
- portview.py reads GL_MAX_TEXTURE_SIZE once (max_texture_size) and halves any image larger than it before its first upload, with one line saying so ("... is larger than this GPU's largest texture (4096 px): uploading it at 1/2 size"), instead of failing with GL_INVALID_VALUE and retrying. SiteStream (a site's imagery streamed in during a run) drops the mip levels over the limit; before, an oversized ring there would have failed and the whole site been given up as Blue Marble only. The size failure used to turn off on-upload compression for every texture (TEXTURES['nocompress']), as its first retry; now compression stays on. Halving 8-bit images is done in 16-bit integers (half_image), the same pixels as before without a float32 copy (1.6 GB for a 16384 x 8192 Blue Marble). On the Pi 5, --test reached "truth data back" at 26 s instead of 35 s.

### [2026-11-17] Target: HANDOFF-meds2-py.md (§12 symptom table)
- Raspberry Pi 5: with NSTS_MEDS_CACHE on (the default), about half of an MDU's frames were black but for the header clock, which looked "garbled" (two seconds' values superimposed); the user saw it as every other screen lost. NOT the bus: the GPC's DK fills arrive complete (every transfer checked against its count; no "transfer abandoned"), and the 157-halfword fill at DYNAMIC 0x1a0e that alternates with the 230-halfword one at 0x1a06 replays into a fresh MDU and draws correctly. The black frames are the repaints that only copy the cached page (clock, flash edge), never a rebuild: Qt clears the QOpenGLWidget's framebuffer before every paintGL (NoPartialUpdate) and the tile-based v3d driver let the clear land after _renderCached's blit. The cached textures read back sound; resetting blend/depth before the blit and NSTS_MEDS_SAMPLES=0 did not help; NSTS_MEDS_CACHE=0 did (and used no more CPU). Fix: MDUGLWidget sets UpdateBehavior.PartialUpdate when _ON_PI5 (the BCM2712 check, now returned by _pi5_gl_override) and the cache is on; the cached path writes every pixel with its blit, so the clear is not needed. Measured on live traffic relayed into a second MDU: 54/100 frames black before, 0/120 after. Other platforms unchanged.
